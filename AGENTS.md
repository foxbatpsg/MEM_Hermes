# Правила работы: от пожеланий к ТЗ

## Начало проекта

Прочитать INDEX.md и docs/wishes.md. Пожелания — свободный текст владельца, не утверждённые требования. Не требовать от пользователя ID, якорей, списка документов или знания конфигурации. Не заменять его слова выдуманными примерами и не перезаписывать исходные пожелания без согласования.

Пока ТЗ нет, corpus и required_ids в governance.json пусты, реестр содержит только заголовок таблицы. Это допустимое стартовое состояние; PASS не означает готовность ТЗ.

## Как ТЗ появляется

1. Изучить пожелания; если они пусты, запросить реальные пожелания, ничего не придумывать.
2. Проверить существующие документы через INDEX.md и адресный поиск перед вопросами. Выделить цели, ограничения, неоднозначности. Предложить структуру ТЗ, но не создавать пустые разделы заранее.
3. Обсудить решения с владельцем. Черновик не становится утверждённым требованием автоматически. Согласования, открытые вопросы, причины и связи с исходными пожеланиями записывать в INDEX.md в разделе решений. Отдельный журнал создавать лишь при реальной необходимости.
4. По мере утверждения создавать нормативные документы, добавлять их пути в corpus (governance.json) и карту INDEX.md одним изменением. Файл пожеланий остаётся исходным материалом вне corpus.
5. Агент назначает постоянные ID: R-001 — требование, Q-001 — вопрос/решение, G-001 — критерий приёмки. Нумерация по каждому префиксу отдельная. Не менять и не переиспользовать ID. При исчерпании диапазона согласованно расширить шаблон, не перенумеровывать старые записи.
6. Каждому действующему требованию — одно определение и одна строка реестра. Индекс хранит адрес, не копию текста. Применения ссылаются по ID. Обязательные согласованные ID (в том числе Gate) вносить в required_ids.

## Формат для агента, не для пользователя

Определение: одна строка `Название (ID): непустой текст`, без Markdown-выделения. Отдельная строка перед ним: `<a id="stable-anchor"></a>`. Между ними допустимы пустые строки. Якорь сохранять при перемещении текста.

Реестр под заголовком `## Реестр`: `ID | Title | Canonical | Status`. ID без форматирования. Canonical — относительный путь с `/` и якорем. Статусы: active — утверждённая запись; open — вопрос без утверждённого определения; gap — намеренно неиспользованный ID; retired — снятая запись с сохранённым историческим определением. Для open/gap адрес равен `—`; определений нет. Основание статуса фиксируется в разделе решений индекса.

## Инструменты индексации

Набор перенесён из проекта-образца (ТЗ 2.4) и адаптирован: ни один скрипт не хранит список
файлов корпуса в коде — область индексации берётся из `governance.json` (ключ `corpus`),
шаблон ID — из `id_pattern`.

- `scripts/validate_index.py` — проверка реестра и корпуса. Дополнительно: ссылки `INDEX.md`
  на Markdown-файлы должны разрешаться; присутствующий генерируемый реестр обязан совпадать
  со своей пересборкой (иначе FAIL).
- `scripts/build_refs_registry.py` — генерирует `REFS-REGISTRY.md` и `REFS-REGISTRY.json`:
  где встречается каждая норма (определения, упоминания, координаты) и разделы корпуса.
  `--check` только сверяет, не перезаписывая. Файлы производные, вручную не правятся.
- `scripts/query_refs.py norm|section|where|stats` — точечные запросы к реестру ссылок.
- `scripts/build_cards_registry.py` + `scripts/query_registry.py` — слой карточек задач.
  Настраивается файлом `cards.json` (список файлов, `id_pattern` по заголовкам `## T-001`,
  `title_pattern`, `task_pattern`, `markers`). Пока карточек нет, файл не создаётся, а скрипты
  сообщают, что слой не настроен.

Порядок проверки после правок корпуса:

```shell
python -B scripts/validate_index.py --strict
python -B scripts/build_refs_registry.py --check
python -B -m unittest discover -s scripts -p "test_*.py"
```

## Правки и проверка

Перед правкой найти Canonical и все затронутые применения. При конфликте остановиться, зафиксировать расхождение в индексе и сообщить владельцу. Не разрешать конфликт самостоятельно. Менять корпус, конфигурацию и индекс согласованно; проверять diff. Не ослаблять проверки ради PASS.

После правок запускать через Python scripts/validate_index.py --strict. После изменения валидатора также запускать unittest discover в scripts. Сообщать код возврата и реальный результат. При работе из другой папки указывать абсолютный путь к скрипту и --root.

Валидатор проверяет только настроенный корпус и реестр, не смысловую полноту, не соответствие пожеланиям и не все ссылки Markdown. Пустой corpus допустим лишь пока утверждённых документов действительно нет. Проверка полноты списка файлов и истории ID — ответственность агента и ревьюера.

Этого файла достаточно для процедуры; отдельный скилл для старта не нужен. Агент должен явно прочитать правила, если среда не загружает AGENTS.md автоматически. Правила не блокируют Git технически; CI и защита ветки настраиваются позже отдельно.
