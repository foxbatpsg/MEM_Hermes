### 1.9. Раздел 3.6. Индексатор

Заменить раздел 3.6 целиком на:

```text
3.6. Индексатор

Индексатор поддерживает производный SQLite/FTS5-индекс.

Индексатор читает файлы журнала текущего проекта инкрементально, используя journal_cursors.
Штатно он обрабатывает только байты после сохранённого смещения.

Индексатор:
- разбирает только полностью завершённые записии журнала;
- дописывает в индекс записии, чьих event_id ещё нет в индексе;
- использует content_hash из метаданных записи журнала и не пересчитывает его
  из обрезанного текста;
- при duplicate event_id считает канонической первую физическую запись по байтовому смещению;
- пропускает повреждённые записии с записью в лог;
- обновляет journal_cursor только после успешной транзакции индексации;
- ограничен по времени и количеству записей за один запуск.

Операция идемпотентна: повторный запуск ничего не меняет. Пропущенная запись дописывается
при следующем запуске, если курсор не был продвинут за неё.

Если файл журнала уменьшился или курсор недействителен, индексатор сбрасывает курсор
для этого файла и переходит в режим полной проверки этого файла либо требует rebuild-index.

Индексатор не удаляет записии журнала.
```

```text
3.7. Режимы работы MiniMem

MiniMem поддерживает независимое включение и отключение основных функциональных подсистем.

3.7.1. Управляемые флаги

Минимально поддерживаются четыре независимых конфигурационных флага:

mode_capture     — запись новых данных в журнал
mode_return      — возврат дайджеста в контекст Hermes
mode_search      — поиск и возврат записей памяти в контекст Hermes
mode_compaction  — выполнение автоматического уплотнения

Значения по умолчанию:

mode_capture = true
mode_return = false
mode_search = false
mode_compaction = false

Состояние одной функции не должно автоматически изменять состояние остальных.

3.7.2. Режимы работы

Рекомендуемые конфигурации:

| Режим                | CAPTURE | RETURN | SEARCH | COMPACTION |
|----------------------|---------|--------|--------|------------|
| Накопление           | ON      | OFF    | OFF    | OFF        |
| Накопление + проверка| ON      | ON     | OFF    | OFF        |
| Рабочий              | ON      | ON     | ON     | ON         |
| Только поиск         | OFF     | OFF    | ON     | OFF        |
| Полностью отключён   | OFF     | OFF    | OFF    | OFF        |

Режимы являются предопределёнными конфигурациями флагов. Архитектура должна позволять
использовать и другие комбинации, если они не нарушают требования настоящего ТЗ.

3.7.3. Рекомендуемый режим разработки

На начальном этапе эксплуатации MiniMem в Hermes рекомендуется использовать:

mode_capture = true
mode_return = false
mode_search = false
mode_compaction = false

В этом режиме MiniMem накапливает реальный журнал, но не влияет на контекст и ответы Hermes.

После проверки журнала и индекса допускается:

mode_capture = true
mode_return = true
mode_search = false
mode_compaction = false

После приёмки возврата:

mode_capture = true
mode_return = true
mode_search = true
mode_compaction = false

После полной приёмки системы:

mode_capture = true
mode_return = true
mode_search = true
mode_compaction = true

Правило 2 уплотнения остаётся отключённым по умолчанию независимо от mode_compaction.
См. раздел 15.1.

3.7.4. Поведение при mode_capture = false

При mode_capture = false:

- хук post_llm_call не создаёт новых записей в журнал;
- автоматический индексатор не запускается;
- существующие журнал, индекс, дайджесты, состояние сессий и suppression state не удаляются
  и не изменяются только вследствие отключения CAPTURE.

Явные CLI-команды rebuild-index, rebuild-digest, verify, show и compact продолжают работать
как административные операции.

3.7.5. Поведение при mode_return = false

При mode_return = false:

- хук pre_llm_call не выполняет Возврат;
- дайджест не вставляется в контекст Hermes;
- автоматическое создание дайджеста при сжатии контекста Hermes не выполняется;
- создание дайджеста на on_session_end и через CLI продолжает работать;
- существующие файлы дайджестов не удаляются и не изменяются только вследствие отключения RETURN.

3.7.6. Поведение при mode_search = false

При mode_search = false:

- хук pre_llm_call не выполняет Поиск;
- найденные записии не вставляются в контекст Hermes;
- если mode_capture = true, индексатор продолжает автоматически индексировать новые записии;
- существующий индекс сохраняется.

3.7.7. Поведение при mode_compaction = false

При mode_compaction = false:

- автоматическое уплотнение не выполняется на on_session_end;
- автоматическое уплотнение не выполняется в catch-up;
- существующие suppression state не изменяются только вследствие отключения COMPACTION;
- явная CLI-команда minimem compact может быть выполнена как административное действие;
- CLI compact уважает флаг compaction_rule2_enabled и не включает правило 2 автоматически.

3.7.8. Независимость функций

- Отключение RETURN или SEARCH не должно отключать CAPTURE.
- Отключение CAPTURE не должно удалять, изменять или переиндексировать уже накопленный журнал.
- Отключение COMPACTION не должно удалять или изменять существующие записии и suppression state.
- Отключение RETURN не удаляет дайджесты.
- Отключение SEARCH не останавливает обновление индекса при работающем CAPTURE.

3.7.9. Переиндексация при переключении режимов

Переключение режимов работы MiniMem не требует переиндексации.

При изменении состояния RETURN, SEARCH или COMPACTION существующие журнал и SQLite/FTS5-индекс
сохраняются без изменений.

Если:

mode_capture = true
mode_search = false

индексатор продолжает автоматически индексировать новые записии.

После переключения:

mode_search = true

поиск использует уже существующий актуальный индекс.

Переиндексация выполняется только в следующих случаях:

- SQLite/FTS5-индекс отсутствует;
- индекс повреждён;
- индекс несовместим с текущей схемой;
- администратор явно запустил rebuild-index.

Обычное переключение режимов не должно автоматически запускать rebuild-index.

3.7.10. Отображение режимов

Команда minimem status обязана показывать активные режимы:

mode_capture
mode_return
mode_search
mode_compaction

А также значения, влияющие на безопасность и эксплуатацию:

compaction_rule2_enabled
journal_fsync
journal_timezone
catch_up_retry_max_turns
catch_up_budget_seconds

Из журнала полностью восстанавливаются:

- FTS5-индекс;
- memory_meta;
- список снятых с поиска — пересчётом по правилам 1 и 3 раздела 15, то есть только по правилам,
  не зависящим от usage_count;
- duplicate event_id обрабатывается детерминированно: канонической считается первая физическая
  запись по байтовому смещению в файле журнала.

Не восстанавливаются:

- usage_count, last_used_at;
- снятие по правилу 2 раздела 15: оно зависит от usage_count, поэтому после пересборки
  не воспроизводится, и снятые только по этому правилу записии возвращаются в поиск;
- состояние текущей сессии;
- best-effort capture_guard может быть восстановлен частично из memory_meta, но его потеря
  не является потерей памяти.

Дайджесты восстанавливаются отдельной командой minimem rebuild-digest.

После пересборки память сохранена, эксплуатационная статистика сброшена. Потеря minimem.db
не означает потерю памяти.
```

### 1.14. Раздел 4.4. Формат одной записи журнала

Заменить раздел 4.4 целиком на:

```text
4.4. Формат одной записи журнала

Файл — UTF-8, переводы строк LF, только дописывание. Записии идут подряд, между ними одна пустая строка.

<!-- mm:begin -->
## 2026-09-22T07:15:42+04:00 · turn 12
- project: mem_hermes
- session_id: 2026-09-22-01
- task_id: task_123
- turn: 12
- event_id: e_3f9c1a…
- content_hash: c_8a1b2d…
- truncated: assistant
### User
текст реплики
### Assistant
текст ответа
<!-- mm:end -->

Правила:

1. Маркер начала — строка `<!-- mm:begin -->`.
2. Маркер конца — строка, точно равная `<!-- mm:end -->`.
3. Порядок метаданных фиксирован:
   project, session_id, task_id, turn, event_id, content_hash, truncated.
4. task_id может быть пустым. Если Hermes не передал task_id, в журнале пишется пустое значение.
5. turn хранит turn_id от Hermes как строку. Если turn_id числовой, он может дополнительно
   нормализоваться в служебном слое для сортировки, но в журнале остаётся строкой.
6. truncated принимает значения: none, user, assistant, both.
7. Тело — две секции: строка `### User` и строка `### Assistant`.
   Текст между ними — реплика; текст после `### Assistant` до маркера конца — ответ.
8. Экранирование тела при записи: строка получает один `\` в начало, если она начинается с `<` или `\`,
   либо точно равна `### User` или `### Assistant`.
9. При чтении у строки тела, начинающейся с `\`, снимается один начальный `\`.
10. Границы записи: запись начинается строкой `<!-- mm:begin -->` и завершается строкой `<!-- mm:end -->`.
11. Если внутри незакрытой записи встречается новая строка, точно равная `<!-- mm:begin -->`,
    предыдущая запись считается повреждённой. Разбор продолжается с новой строки `<!-- mm:begin -->`.
12. Запись без маркера конца в конце файла считается повреждённой.
13. Повреждённая запись пропускается с записью в лог как journal_record_damaged.
14. Разбор опирается только на маркеры и на строки `### User` / `### Assistant`;
    заголовки и разметка внутри текста на разбор не влияют.
```

```text

Полнотекстовые поля:

assistant_answer

Служебные поля индексной записи хранятся в таблице memory_meta и в полнотекстовом поиске

Оценка релевантности: score = -bm25(...); больше — лучше. bm25() в FTS5 возвращает

То же самое напрямую через bm25: bm25(...) <= -search_score_threshold. Направление
сравнения фиксируется здесь потому, что в шкале bm25 «меньше — лучше», и сравнение
с порогом в другой шкале даёт обратный результат.

journal_file и journal_offset — подсказка для быстрого доступа. Запись ищется по event_id;

встроенный porter знает только английский, а русская морфология в FTS5 отсутствует.

Механизм раздела 12 — детерминированное усечение русских слов по фиксированному набору
окончаний + prefix-поиск FTS5. Это не морфологический стеммер и не лемматизация: список
окончаний неизбежно даёт ошибки — одна основа может соответствовать разным словам,
а часть форм обрабатывается неправильно. Для MiniMem-1 это допустимо: цель не лингвистическая
корректность, а увеличение recall поиска при минимальной сложности.

Токенизатор trigram (поиск по подстроке) рассмотрен и отвергнут: индекс раздувается,

нейтрализуются до построения запроса.

9.2. Инкрементальная индексация

Индексатор не должен при каждом запуске читать весь дневной файл журнала.

Алгоритм:

1. Определить файлы журнала текущего проекта, требующие обработки.
2. Для каждого файла прочитать journal_cursor.
3. Если курсор отсутствует, начать с byte_offset = 0.
4. Проверить, что файл не уменьшился относительно file_size из курсора.
5. Если файл уменьшился или курсор недействителен, сбросить byte_offset = 0
   и залоировать cursor_reset.
6. Читать файл с byte_offset.
7. Разбирать только полностью завершённые записии.
8. Если в конце файла найдена неполная запись, не продвигать курсор за её начало.
9. Индексировать записии, чьих event_id нет в индексе.
10. При duplicate event_id пропускать последующую физическую запись
    и залоировать journal_duplicate_event_id.
11. После успешной транзакции обновить byte_offset до конца последней обработанной полной записи.
12. Один запуск ограничен post_llm_timeout и максимальным числом записей за проход.

Курсор обновляется только после успешной индексации.

Если индексатор упал до обновления курсора, запись будет повторена при следующем запуске.
Повторная индексация идемпотентна по event_id.

- новые записии в журнал не создаются;
- автоматический индексатор не запускается;
- событие логируется как capture_disabled.

Если mode_capture = true, последовательность:

1. получить завершённый ход — реплику и ответ;
2. проверить session_id и turn;
3. определить проект;
4. выполнить redaction с детерминированными placeholder'ами;
5. канонизовать полное содержимое после redaction;
6. вычислить content_hash;
7. обрезать поля по лимитам;
8. обеспечить max_memory_record;
9. вычислить event_id;
10. проверить idempotency и конфликт по event_id, если SQLite доступен;
11. атомарно дописать запись в журнал под блокировкой;
12. при успешной записи и доступном SQLite обновить capture_guard.

Данные хода берутся из события post_llm_call:
extra.user_message, extra.assistant_response, extra.turn_id, extra.task_id,
session_id, cwd.

Если SQLite недоступен:

- Capture всё равно пишет запись в журнал;
- логируется capture_idempotency_guard_unavailable.

Захват не обновляет полнотекстовый индекс: это делает Индексатор отдельным запуском.

Ошибка записи в журнал логируется; Hermes продолжает работу.
```

### 1.23. Раздел 11. Возврат (Return)

Заменить раздел 11 целиком на:

```text
11. Возврат (Return)

Возврат срабатывает на первом ходе новой сессии и после сжатия контекста Hermes,
но только при mode_return = true.

Что именно возвращается:

- первый ход новой сессии — выжимка предыдущей сессии: последний валидный файл дайджеста проекта
  по правилам раздела 11.1, кроме файла текущей сессии; файла нет — не вставляет ничего;
- сжатие контекста Hermes — выжимка текущей сессии: файл дайджеста текущей сессии.
  Файла нет — его создаёт модуль Дайджест из журнала той же функцией, что и на on_session_end;
  создать не удалось или ходов в сессии нет — не вставляет ничего;
- если на одном ходу есть оба признака, работает правило первого хода.

Как определяется сжатие контекста. Hermes не передаёт признак сжатия: в событии хода есть только
session_id, cwd, task_id, turn_id, user_message, conversation_history, is_first_turn, model,
platform, parent_session_id, sender_id, profile. Поэтому сжатие вычисляет сам MiniMem
по уменьшению истории:

hist_len         = len(conversation_history_without_minimem) на текущем ходу
max_history_len  = наибольшая hist_len, ранее наблюдавшаяся в этой сессии (раздел 17)

conversation_history_without_minimem — это conversation_history, из сообщений которой
перед измерением удалены блоки памяти MiniMem по делимитерам раздела 13.

Сжатие состоялось, если:

  max_history_len >= compaction_min_drop
  AND hist_len < max_history_len * compaction_shrink_ratio
  AND (max_history_len - hist_len) >= compaction_min_drop

Обновление max_history_len каждый ход: если сжатие на этом ходу не обнаружено —
max_history_len = max(max_history_len, hist_len); если обнаружено — max_history_len = hist_len.

То есть после сжатия точка отсчёта берётся заново: иначе уменьшение истории продолжало бы
выполнять условие на следующих ходах, и Возврат вставлял бы выжимку повторно.

Флаг is_first_turn — самостоятельный триггер и имеет приоритет: если он установлен,
работает правило первого хода.

Возврат:

- читает только файл дайджеста;
- не выполняет поиск;
- не читает журнал напрямую: при сжатии контекста журнал читает Дайджест, а не Возврат;
- не вызывает модель;
- не увеличивает счётчик использования;
- возвращает объём не более max_return_chars.

Поиск в этом ходу не запускается.

Возврат и Поиск — независимые модули. Они не координируют работу через текстовые файлы
или другие хрупкие механизмы.

11.1. Детерминированный выбор дайджеста

Последним дайджестом проекта считается файл с максимальным значением поля "Создан"
в заголовке дайджеста, нормализованным в UTC.

Порядок выбора:

1. Исключить файл текущей сессии.
2. Прочитать поле "Создан" из заголовка каждого валидного дайджеста.
3. Выбрать максимальный timestamp_utc.
4. При равенстве выбрать меньшее имя файла в лексикографическом порядке.
5. При невозможности прочитать "Создан" использовать mtime файла как fallback
   и залоировать digest_mtime_fallback.
6. Повреждённый дайджест пропускается; Return не падает и может выбрать следующий валидный файл.

Имя файла дайджеста должно быть filesystem-safe.

Санитизация session_id для имени файла:

- запрещённые символы: / \ : * ? " < > |
- управляющие символы удаляются;
- длина ограничивается 120 символами;
- при коллизии имени добавляется суффикс _<первые 8 hex-символов sha256(session_id)>.
```

### 1.24. Раздел 12. Хук Поиска (Search Hook)

Заменить раздел 12 целиком на:

```text
12. Хук Поиска (Search Hook)

Хук: pre_llm_call.

Поиск выполняется только при mode_search = true.

Условия запуска:
- реплика содержательная; короткие и служебные реплики пропускаются;
- ход не является тем, на котором работает Возврат;
- после нормализации осталось хотя бы одно поисковое term.

Последовательность:

1. получить реплику пользователя;
2. ограничить её длину и нормализовать;
3. построить запрос кодом, нейтрализовав операторы FTS5:
   - разбить реплику на слова: разделители — всё, кроме букв и цифр; кириллица и латиница равноправны;
   - отбросить слова короче search_min_word_len;
   - каждое слово усечь до основы: отбросить окончание по фиксированному списку окончаний
     (самые длинные — первыми), но не короче search_stem_min_len. Это детерминированное усечение,
     не морфологический стеммер (раздел 9);
   - удалить дубликаты основ с сохранением первого порядка появления;
   - ограничить количество основ max_search_terms;
   - если после ограничения осталось 0 основ, поиск не запускается;
   - каждую основу заключить в двойные кавычки и добавить * — получается, например, "памят"*;
   - основы объединить через OR.

Запрос собирается только из слов, прошедших нормализацию: текст пользователя в запрос не попадает,
поэтому операторы FTS5 нейтрализуются самим построением. Список окончаний — константа в коде,
детерминированная, без модели и без внешних библиотек.

4. ограничить поиск текущим проектом;
5. исключить записии, снятые с поиска;
6. исключить записии, уже возвращённые в текущей сессии;
7. выполнить поиск FTS5;
8. применить порог search_score_threshold (шкала score, больше — лучше; см. раздел 9);
9. выбрать не более max_return_records;
10. ограничить общий объём max_return_chars;
11. увеличить usage_count и обновить last_used_at у возвращённых записей;
12. отметить возвращённые записии в состоянии сессии;
13. вставить результат в контекст по разделу 13.

12.1. Ограничения построения поискового запроса

После извлечения основ:

1. Дубликаты основ удаляются с сохранением первого порядка появления.
2. Количество основ ограничивается max_search_terms.
   Значение по умолчанию: 8.
3. Если после нормализации осталось 0 терминов, поиск не запускается.
4. Пользовательский текст не попадает в FTS5-запрос напрямую.
5. Запрос собирается только из нормализованных основ.
6. Операторы FTS5 нейтрализуются самой конструкцией запроса.
```

### 1.27. Раздел 15. Уплотнение (Compaction)

Заменить раздел 15 целиком на:

```text
15. Уплотнение (Compaction)

Уплотнение не меняет журнал.

Запись снимается с поиска, если выполняется хотя бы одно:

1) возраст > compaction_age

2) usage_count = 0
   AND возраст > compaction_unused_age
   AND запись создана после последней пересборки (timestamp_utc > rebuilt_at)
   И compaction_rule2_enabled = true

3) существует другая запись того же проекта с тем же content_hash

По правилу 3 остаётся первая запись — с меньшим timestamp_utc,
при равенстве — с меньшим turn_numeric, если он числовой,
при равенстве или отсутствии turn_numeric — с меньшим turn как строкой,
затем по event_id.

Точный дубль определяется по content_hash, вычисленному до обрезки.
Точный дубль определяется внутри одного проекта: одинаковое содержимое в разных проектах
дублем не считается и с поиска не снимается.

Механические признаки: возраст записи, отсутствие использования, точное дублирование.

Уплотнение не выполняет семантическое объединение и не разрешает конфликты.

Снятая запись:

- не удаляется из журнала;
- не возвращается Поиском;
- не попадает в дайджест.

К Возврату признак неприменим: Возврат читает дайджест, а не записии журнала.

Список снятых записей хранится в служебном слое и ссылается на event_id.

Восстановление после пересборки индекса. При rebuild-index список снятых записей
пересчитывается заново только по правилам 1 и 3 — тем, которые определяются журналом
и не зависят от usage_count. Правило 2 после пересборки воспроизвести нельзя: счётчики обнулены,
поэтому запись, снятая ранее только по правилу 2, возвращается в поиск. Для записей,
созданных после пересборки, правило 2 работает в обычном порядке, если включён
compaction_rule2_enabled.

15.1. Отключаемые правила уплотнения

Правило 2 уплотнения по умолчанию отключено:

compaction_rule2_enabled = false

Правило 2 выполняется только если compaction_rule2_enabled = true.

Обоснование:

usage_count = 0 не означает, что запись не важна.
При лексическом поиске это может означать, что поиск не нашёл запись.
Поэтому включение правила 2 допускается только после отдельной приёмки
на реальных данных эксплуатации. Решение отслеживается в реестре доработок, запись RB-01.

Правила 1 и 3 остаются базовыми.

Автоматическое уплотнение выполняется только при mode_compaction = true.
Явная CLI-команда compact может выполняться при mode_compaction = false
как административное действие, но уважает compaction_rule2_enabled.
```

### 1.30. Раздел 18. Жизненный цикл хуков (Hook Lifecycle)

Заменить раздел 18 целиком на:

```text
18. Жизненный цикл хуков (Hook Lifecycle)

Событие on_session_start в Hermes есть, но оно не вставляет текст в сообщение модели
и не несёт cwd. Поэтому и catch-up, и Возврат выполняются на первом pre_llm_call сессии,
когда Hermes передаёт флаг первого хода.

Первый ход сессии

pre_llm_call (первый ход)
  ↓
если mode_return = true или mode_compaction = true, выполняется catch-up по разделу 18.1
  ↓
Возврат — если mode_return = true, читает дайджест предыдущей сессии
  ↓
Поиск не запускается

Каждый ход

pre_llm_call
  ├─ Дайджест — только если сжатие контекста Hermes и mode_return = true
  ├─ Возврат — если mode_return = true и это первый ход или сжатие контекста Hermes
  └─ Поиск — если mode_search = true и во всех остальных ходах
  ↓
модель Hermes
  ↓
post_llm_call
  ├─ Захват — если mode_capture = true
  └─ Индексатор — если mode_capture = true

Конец сессии

on_session_end
  ├─ Уплотнение — если mode_compaction = true
  └─ Дайджест — создаётся независимо от mode_return, если есть записии сессии

Catch-up не является функцией Возврата. Если catch-up не укладывается в отведённое время,
он прерывается, пишется в лог, pending_catch_up сохраняется, attempts увеличиваются,
и Возврат всё равно выполняется: он читает уже существующий файл дайджеста, а если файла нет —
не вставляет ничего.

18.1. Catch-up

Catch-up выполняется на первом ходе новой сессии и, при неудаче, ограниченно повторяется
в этой же сессии.

Политика по умолчанию — вариант A:

catch_up_retry_max_turns = 2
catch_up_budget_seconds = 8

Компоненты catch-up управляются режимами независимо:

- уплотнение предыдущей сессии выполняется только при mode_compaction = true;
- создание дайджеста предыдущей сессии выполняется только при mode_return = true;
- если оба режима выключены, автоматический catch-up не выполняется.

Алгоритм первого хода:

1. Определить текущий проект и session_id.
2. Создать или обновить состояние текущей сессии.
3. Найти предыдущую сессию проекта:
   - последняя сессия того же проекта, отличная от текущей;
   - сортировка по last_seen_at DESC, затем session_id DESC.
4. Если состояние сессий потеряно после rebuild-index:
   - автоматический catch-up не сканирует весь журнал;
   - логируется catch_up_state_unavailable;
   - уплотнение в catch-up не выполняется автоматически;
   - если mode_return = true, Return использует только существующие валидные дайджесты;
   - полное восстановление — через CLI rebuild-digest.
5. Если у предыдущей сессии digest_status != done или файл дайджеста отсутствует/повреждён
   и mode_return = true:
   5.1. Выполнить построение дайджеста предыдущей сессии в рамках бюджета времени.
   5.2. Если дайджест успешно создан, установить digest_status = done.
6. Если mode_compaction = true и бюджет позволяет, выполнить уплотнение для предыдущей сессии/проекта.
7. Если бюджет времени исчерпан:
   7.1. Установить pending_catch_up = true.
   7.2. Увеличить catch_up_attempts.
   7.3. Залоировать catch_up_timeout.
   7.4. Перейти к Return с уже существующими данными.
8. Если catch-up завершён успешно, снять pending_catch_up.
9. Return читает дайджест предыдущей сессии, если mode_return = true и дайджест существует.
10. Если дайджеста нет, Return ничего не вставляет.
11. Поиск на первом ходе не запускается.

Повтор catch-up:

- повтор выполняется только если catch_up_attempts < catch_up_retry_max_turns;
- повтор происходит на следующих ходах той же сессии, не более указанного лимита;
- в новой сессии attempts для новой текущей сессии сбрасываются;
- если catch-up не завершён, допускается ручной запуск CLI.

Идемпотентность:

- повторный catch-up не должен повторно создавать дублирующиеся дайджесты;
- пересоздание дайджеста перезаписывает тот же файл;
- если digest_status = done и файл валиден, создание дайджеста не выполняется;
- уплотнение идемпотентно по suppression state.

Возможный переход к более агрессивной политике catch-up рассматривается после накопления статистики
эксплуатации. Решение отслеживается в реестре доработок, запись RB-02.
```

## 4. Правила работы по плану

Один этап — одна законченная функциональная подсистема / зона ответственности.
Следующий этап не начинается, пока не пройдены тесты предыдущего.
Тесты пишутся в том же этапе, что и код, и несут номер из раздела 23 ТЗ.
Тест нельзя удалить: только перевести в статус «снят» с указанием причины.
Заглушек «потом доделаю» не бывает. Если функциональность не входит в MiniMem-1, она не пишется вовсе.
Любая ошибка перехватывается на границе хука: запись в лог, пустой вывод, Hermes продолжает работу.
Изменение поведения сначала вносится в ТЗ, затем в код.
Журнал копируется в бэкап ежедневно, начиная с этапа 1.
Отложенные эксплуатационные решения фиксируются в реестре доработок.

## 5. Что не входит в реализацию

Без изменений от v1.5, плюс:
- автоматическое включение правила 2 уплотнения без RB-01;
- агрессивный catch-up варианта B без RB-02;
- фоновый maintenance индексатора.
