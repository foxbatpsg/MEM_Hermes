## P0-1. Режимы CAPTURE / RETURN / SEARCH / COMPACTION есть в ТЗ, но отсутствуют в конфигурации, плане и тестах

В ТЗ есть раздел X с управляемыми функциями:

- `CAPTURE`
- `RETURN`
- `SEARCH`
- `COMPACTION`

И даже рекомендованный режим разработки:

```text
CAPTURE=ON
RETURN=OFF
SEARCH=OFF
COMPACTION=OFF
```

Но в разделе 20 «Конфигурация» этих флагов нет. В плане реализации тоже нет ни модуля, ни этапа, ни тестов, которые явно покрывают режимы.

Это противоречие.

### Почему это критично

Если режимы не реализованы, нельзя безопасно включать MiniMem в Hermes. Рекомендуемый режим накопления — важная часть эксплуатации. Без него система сразу начинает влиять на контекст, хотя должна сначала просто писать журнал.

Кроме того, из раздела X следуют неочевидные требования:

- отключение `RETURN` не должно отключать `CAPTURE`;
- отключение `SEARCH` не должно останавливать индексацию при работающем `CAPTURE`;
- отключение `COMPACTION` не должно менять существующие suppression state;
- переключение режимов не должно требовать переиндексации;
- Digest может продолжаться даже при `RETURN=OFF`.

Это надо явно кодировать и тестировать.

### Что предлагаю

Добавить в §20 конфигурации, например:

```json
{
  "modes": {
    "capture": true,
    "return": false,
    "search": false,
    "compaction": false
  }
}
```

Или плоские ключи:

```text
mode_capture
mode_return
mode_search
mode_compaction
```

Добавить в `minimem status` отображение активных режимов.

Добавить в хуки явные гейты:

- `post_llm.py`:
  - если `CAPTURE=OFF`, не писать журнал;
  - если `CAPTURE=ON`, писать журнал;
  - индексатор запускать при `CAPTURE=ON` или при явной необходимости догоняющей индексации.
- `pre_llm.py`:
  - если `RETURN=OFF`, не вставлять дайджест;
  - если `SEARCH=OFF`, не искать;
  - catch-up/digest lifecycle должен соблюдаться независимо от `RETURN`, если ТЗ требует, чтобы дайджест продолжал создаваться.
- `session_end.py`:
  - `COMPACTION=OFF` — не выполнять уплотнение;
  - дайджест создавать независимо от `RETURN`, если это требуется разделом X.

Добавить тесты, например:

- `MM-51`: при `CAPTURE=OFF` новые записи в журнал не создаются.
- `MM-52`: при `RETURN=OFF` дайджест всё равно создаётся на `on_session_end`.
- `MM-53`: при `SEARCH=OFF` индексатор продолжает работать при `CAPTURE=ON`.
- `MM-54`: при `COMPACTION=OFF` существующие suppression state не меняются.
- `MM-55`: переключение режимов не требует `rebuild-index`.

Если не хотите расширять нумерацию, можно включить эти проверки в существующие тесты, но лучше добавить отдельные номера. Для приёмки агентной системы такие режимы слишком важны, чтобы оставлять их неявными.

## P0-2. В схеме SQLite явно не указаны `session_id` и `turn`, хотя без них невозможны дайджест, поиск, вставка и уплотнение

В §4.2 и §9 перечислены служебные колонки SQLite:

- `event_id`
- `content_hash`
- `project`
- `timestamp`
- `journal_file`
- `journal_offset`

Но там нет:

- `session_id`
- `turn`

При этом система обязана:

- строить дайджест по `session_id` (§14);
- исключать уже возвращённые записи в текущей сессии (§12, §17);
- вставлять в контекст дату, проект, сессию, ход и источник (§13);
- при правиле 3 уплотнения оставлять первую запись по `timestamp`, а при равенстве — по меньшему `turn` (§15);
- проверять наличие дайджеста у завершённых сессий (§21 `verify`);
- хранить состояние сессий (§17).

Без `session_id` и `turn` в индексе это невозможно сделать эффективно и корректно.

### Почему это критично

Это не мелочь. Это прямая нестыковка между форматом журнала, требованиями к поиску/дайджесту и описанием SQLite-схемы.

Если разработчик начнёт Этап 2 по текущему тексту, ему придётся самостоятельно решать:

- добавлять ли колонки;
- где хранить `session_id`;
- как фильтровать по сессии;
- как сортировать дубликаты по ходу;
- как восстанавливать дайджесты по журналу, не парся весь файл каждый раз.

Это нарушает принцип «сначала ТЗ, потом код».

### Что предлагаю

Явно добавить в §4.2 и §9 служебные колонки:

```text
session_id
turn
truncated
```

Как минимум:

- `session_id TEXT NOT NULL`
- `turn INTEGER NOT NULL`
- `truncated TEXT NOT NULL` — `none`, `user`, `assistant`, `both`

Желательно также добавить:

- индекс по `project, session_id, turn`;
- индекс по `project, timestamp`;
- индекс по `content_hash, project`;
- уникальный индекс по `event_id`.

Для FTS5-таблицы эти колонки должны быть `UNINDEXED`, чтобы не участвовать в полнотекстовом поиске, но доступны для SQL-фильтрации.

Примерно схема может выглядеть так:

```sql
CREATE VIRTUAL TABLE memory USING fts5(
  user_utterance,
  assistant_answer,
  event_id UNINDEXED,
  content_hash UNINDEXED,
  project UNINDEXED,
  session_id UNINDEXED,
  turn UNINDEXED,
  timestamp UNINDEXED,
  truncated UNINDEXED,
  journal_file UNINDEXED,
  journal_offset UNINDEXED,
  tokenize = 'unicode61'
);
```

Отдельно:

- `usage_counters(event_id, usage_count, last_used_at)`
- `suppressed(event_id, reason, suppressed_at)`
- `sessions(session_id, project, last_known_turn, max_history_len, digest_status, pending_catch_up)`
- `session_returns(session_id, event_id, returned_at)`
- `journal_cursors(journal_file, byte_offset, size, mtime, updated_at)`

Это сделает производный слой действительно пригодным для работы.

## P0-3. `event_id` включает содержимое, что противоречит требованию «один завершённый ход — одна запись» при ретраях

Сейчас:

```text
event_id = "e_" + sha256(project + session_id + turn + canonical_content)
```

То есть идентичность события зависит от содержимого.

Но в §1 и §5 сказано:

> Один завершённый ход диалога образует одну запись журнала.

Проблема: если Hermes или хук повторно доставит тот же ход, но с немного другим ответом — например, после сбоя, таймаута, перегенерации, изменения truncation/redaction — получится другой `event_id`. Тогда идемпотентность по `event_id` не сработает, и в журнал попадёт вторая запись для того же логического хода.

Это нарушает инвариант «один ход — одна запись».

### Почему это критично

Для агентной памяти это серьёзно. Повторы одного и того же хода с разными формулировками ответа могут:

- засорять поиск;
- попадать в дайджест;
- создавать ложные дубликаты/конфликты;
- увеличивать `usage_count` некорректно;
- делать поведение памяти невоспроизводимым.

Сейчас ТЗ пытается решить идемпотентность через содержимое, но это слабее, чем идентичность по логическому ходу.

### Что предлагаю

Я бы изменил определение `event_id`.

Вариант A, самый простой и правильный для v1:

```text
event_id = "e_" + sha256(project + "\n" + session_id + "\n" + turn)
```

или, если Hermes стабильно передаёт `task_id`/`turn_id`:

```text
event_id = "e_" + sha256(project + "\n" + session_id + "\n" + task_id + "\n" + turn)
```

А содержимое учитывается только в `content_hash`.

Тогда:

- повторная доставка того же хода с тем же содержимым — идемпотентна;
- повторная доставка того же хода с другим содержимым — тоже не создаёт вторую запись, а логируется как конфликт;
- две одинаковые реплики на разных ходах по-прежнему дают разные `event_id`, потому что различается `turn`;
- тест 7 остаётся корректным.

Нужно явно описать поведение при конфликте:

> Если `event_id` уже существует в журнале/индексе, но `content_hash` отличается, новая запись не дописывается. Событие логируется как `capture_event_conflict`. Hermes продолжает работу.

Это жёстче, но сохраняет инвариант одного хода.

Вариант B, если вы принципиально хотите сохранять обе попытки:

Тогда нужно изменить формулировку ТЗ:

> Один завершённый ход может образовать одну или несколько записей при повторных доставках с различным содержимым. Для памяти используется последняя по времени запись хода, либо все записи считаются отдельными событиями.

Но это усложняет дайджест, поиск и уплотнение. Для MiniMem-1 я бы не шёл по этому пути.

Моя рекомендация: вариант A.

## P0-4. `content_hash` вычисляется после обрезки, что может создавать ложные дубликаты

Сейчас порядок:

1. удаление секретов;
2. обрезка по лимитам;
3. канонизация;
4. `content_hash` и `event_id`.

Проблема: две разные длинные записи могут после обрезки стать одинаковыми по префиксу. Тогда `content_hash` совпадёт, хотя полное содержимое различается.

Это особенно опасно для правила 3 уплотнения:

> существует другая запись того же проекта с тем же `content_hash`

Если хеш посчитан по обрезанному содержимому, система может снять с поиска и из дайджеста запись, которая не является настоящим дубликатом.

### Почему это критично

Журнал не удаляется, но запись перестаёт возвращаться поиском и не попадает в дайджест. С точки зрения пользователя это выглядит как потеря памяти.

Для агентной памяти это недопустимо: механическое уплотнение не должно создавать ложных потерь релевантности.

### Что предлагаю

Изменить порядок вычисления хешей.

Предлагаемый порядок:

1. получить данные хода;
2. удалить секреты;
3. канонизировать полное содержимое после редации;
4. вычислить `content_hash` по полному каноническому содержимому;
5. обрезать поля по лимитам;
6. канонизировать обрезанное представление для хранения;
7. вычислить `event_id` по стабильной идентичности хода;
8. записать в журнал `content_hash`, полученный до обрезки.

То есть `content_hash` должен отражать полное отредактированное содержимое, а не обрезанный текст.

Если нельзя менять порядок из-за совместимости, минимум — включить в хеш метаданные обрезки:

```text
content_hash = sha256(
  canonical_full_or_truncated +
  "\n" + user_original_length +
  "\n" + assistant_original_length +
  "\n" + truncated_flag
)
```

Но лучше просто хешировать полное содержимое до обрезки.

Важно: индексатор не должен пересчитывать `content_hash` из обрезанного текста журнала. Он должен использовать значение из метаданных записи.

## P0-5. Формат журнала уязвим к частичной записи и вложенным `mm:begin`

Сейчас граница записи:

> от строки маркера начала до первой строки, точно равной маркеру конца.

Проблема: если процесс упал посреди записи, в файле может остаться неполная запись без `mm:end`. Следующая запись будет дописана после неё. Тогда парсер, идя от первого `mm:begin`, дойдёт до `mm:end` уже второй записи и может ошибочно склеить повреждённую запись со следующей.

То есть частичная запись может «съесть» следующую корректную запись.

Кроме того, если внутри текста появится строка `<!-- mm:begin -->`, она экранируется как начинающаяся с `<`, поэтому в теле не должна встречаться как точный маркер. Но при частичной записи это не спасает.

### Почему это критично

Журнал — источник истины. Если парсер может потерять целую запись из-за аварийного завершения, это подрывает главную гарантию системы.

Для хуков, работающих под таймаутами и в условиях возможного kill процесса, это реальный сценарий.

### Что предлагаю

Нужны два механизма.

#### 1. Атомарная запись всей записи

Запись должна формироваться целиком в памяти и дописываться одним системным вызовом под блокировкой.

Например:

```python
record_bytes = serialize_record(...).encode("utf-8")
with lock:
    fd.write(record_bytes)
    fd.flush()
    os.fsync(fd.fileno())
```

На Windows `os.fsync` может быть дороже, но для надёжности источника истины это приемлемо. Можно делать `fsync` не на каждый ход, если производительность критична, но тогда риск потери при ОС-сбое выше. Для v1 я бы оставлял `flush`, а `fsync` сделал конфигурируемым или включённым по умолчанию.

#### 2. Изменить правило разбора

Добавить правило:

> Если внутри записи до маркера конца встречается строка, точно равная `<!-- mm:begin -->`, текущая запись считается повреждённой. Разбор продолжается с этой новой строки `<!-- mm:begin -->`.

То есть парсер не должен искать первый `mm:end` после первого `mm:begin`, если между ними появился новый `mm:begin`.

Псевдокод:

```text
state = OUTSIDE
for line in file:
  if line == BEGIN:
    if state == INSIDE:
      mark previous record damaged
    start new record
    state = INSIDE
  elif line == END and state == INSIDE:
    complete record
    state = OUTSIDE
```

Это спасает от частичной записи перед следующей корректной записью.

Дополнительно можно добавить в маркер начала длину записи или хеш, но для MiniMem-1 это, возможно, избыточно. Главное — правило вложенного `begin`.

## P0-6. Не описан инкрементальный курсор индексатора, из-за чего `post_llm_call` может деградировать по времени

В ТЗ сказано, что индексатор читает дневной файл журнала и дописывает в индекс записи, чьих `event_id` ещё нет.

Но не сказано, как именно он понимает, какие записи уже просмотрены.

Если каждый запуск индексатора сканирует весь дневной файл, то к концу дня это станет O(N). При активном использовании Hermes это легко может превысить 30 секунд на `post_llm_call`.

### Почему это критично

Индексатор вызывается после каждого хода. Если он каждый раз читает весь журнал дня, система деградирует линейно в течение дня.

Это прямой риск таймаутов и отказа памяти.

### Что предлагаю

Добавить в SQLite служебное состояние курсора:

```text
journal_cursors(
  journal_file TEXT PRIMARY KEY,
  byte_offset INTEGER,
  file_size INTEGER,
  mtime REAL,
  last_error TEXT,
  updated_at TEXT
)
```

Логика индексатора:

1. определить текущий дневной файл проекта;
2. взять сохранённый `byte_offset`;
3. проверить, что файл не уменьшился и mtime/size совместимы;
4. читать с `byte_offset`;
5. разбирать только полностью завершённые записи;
6. индексировать недостающие `event_id`;
7. обновить `byte_offset` после последней успешно обработанной записи;
8. при подозрении на повреждение/редактирование файла — переходить в режим полной проверки или требовать `rebuild-index`.

Важно: курсор должен обновляться только после успешной транзакции индексации.

Также нужно ограничить один проход индексатора по времени и количеству записей. Если записей слишком много, индексатор может обработать часть и оставить остаток на следующий запуск.

Это соответствует требованию самовосстановления: пропущенная запись дописывается при следующем запуске.

## P0-7. Catch-up на первом ходе недостаточно специфицирован

В §18 сказано:

> Первый ход сессии: catch-up: Уплотнение, затем Дайджест предыдущей сессии.

Но не до конца определено:

- как найти «предыдущую сессию»;
- что считать предыдущей сессией, если сессий много;
- как понять, что дайджест уже создан;
- что делать, если `on_session_end` не был вызван;
- как хранить `pending_catch_up`;
- как избежать повторного тяжёлого catch-up на каждом ходе;
- что делать, если catch-up не укладывается в 15 секунд;
- как соотносятся `RETURN=OFF`, `COMPACTION=OFF`, `CAPTURE=OFF` и catch-up.

### Почему это критично

Catch-up выполняется в `pre_llm_call`, то есть в самом жёстком таймауте. Если он недетерминирован или тяжёл, первая сессия после сбоя может тормозить или не получить память.

### Что предлагаю

Нужно добавить в ТЗ явный алгоритм.

Например:

#### Состояние сессии

В таблице `sessions` хранить:

```text
session_id
project
last_known_turn
max_history_len
digest_status: none | pending | done | failed
pending_catch_up: bool
completed: bool
last_seen_at
```

#### Определение предыдущей сессии

На первом ходе новой сессии в проекте:

1. найти последнюю сессию того же проекта, отличную от текущей;
2. если у неё `digest_status != done` или файл дайджеста отсутствует/повреждён — поставить catch-up;
3. если `COMPACTION=ON`, выполнить уплотнение для этой сессии/проекта в рамках бюджета времени;
4. выполнить построение дайджеста предыдущей сессии;
5. обновить `digest_status=done`;
6. снять `pending_catch_up`.

#### Ограничение по времени

Catch-up должен иметь внутренний бюджет, например 10 секунд из 15, оставляя 5 секунд на Return и службу логов.

Если не успевает:

- записать `pending_catch_up=true`;
- залогировать `catch_up_timeout`;
- Return выполняет работу с уже существующим дайджестом;
- если дайджеста нет — Return ничего не вставляет.

#### Идемпотентность

Catch-up должен быть идемпотентным:

- повторный запуск не должен повторно уплотнять то же самое без необходимости;
- повторное создание дайджеста перезаписывает тот же файл;
- если `digest_status=done` и файл валиден, catch-up не выполняется.

#### Взаимодействие с режимами

Нужно явно сказать:

- при `COMPACTION=OFF` catch-up пропускает уплотнение, но может создавать дайджест, если дайджест не зависит от compaction;
- при `RETURN=OFF` catch-up всё равно может создавать дайджест для будущей работы;
- при `CAPTURE=OFF` catch-up может работать с уже существующим журналом, но новые записи не появятся.

Без этой спецификации разработчик будет придумывать поведение сам.

# 3. Серьёзные риски, которые нужно закрыть в v1 или явно принять

Ниже — не обязательно блокеры, но вещи, которые могут сильно испортить эксплуатацию.

---

## 3.1. Эвристика определения сжатия контекста Hermes может давать ложные срабатывания

MiniMem сам вычисляет сжатие контекста по длине `conversation_history`:

```text
hist_len < max_history_len * compaction_shrink_ratio
AND (max_history_len - hist_len) >= compaction_min_drop
```

Это разумно, потому что Hermes не передаёт явный признак. Но эвристика хрупкая.

### Риски

Ложные срабатывания возможны, если:

- пользователь удалил часть истории вручную;
- Hermes меняет формат истории;
- в историю попадают/не попадают служебные сообщения;
- память MiniMem сама увеличивает историю, а затем она сокращается;
- разные платформы дают разную структуру `conversation_history`;
- история содержит tool messages, которые могут исчезать/появляться.

Ложные пропуски возможны, если:

- сжатие уменьшает историю не сильно;
- `compaction_min_drop` слишком велик;
- история и так короткая.

### Что предлагаю

Добавить защитные механизмы:

1. **Cooldown**: не вставлять дайджест текущей сессии чаще одного раза за N ходов после обнаружения сжатия.
2. **Логирование**: всегда писать `context_compaction_detected`, `hist_len`, `max_history_len`, `drop`, `ratio`.
3. **Тесты на ложные срабатывания**:
   - история уменьшилась на 1;
   - история уменьшилась ниже порога, но это не compaction;
   - история содержит вставку MiniMem;
   - несколько compaction подряд.
4. Возможно, использовать не только длину списка, но и оценку токенов/символов, если Hermes это доступно. Но для v1 можно оставить длину, главное — cooldown и наблюдаемость.

Также важно: вставленная MiniMem память попадает в сообщение пользователя. Значит, `conversation_history` на следующем ходу может быть длиннее из-за самой памяти. Это может искажать `max_history_len`. Нужно явно решить, учитывать ли память в истории для детекции сжатия. Я бы рекомендовал либо очищать историю от блоков MiniMem перед измерением, либо документировать, что измерение включает память и поэтому пороги подобраны с запасом.

## 3.2. Поиск по русской морфологии через усечение основы — приемлемый компромисс, но требует дисциплины

Раздел 12 делает правильное для v1 решение: не тянуть pymorphy, не использовать embeddings, сделать детерминированное усечение окончаний + prefix search.

Но это механизм с заведомо низкой точностью.

### Ожидаемые проблемы

- переобобщение: одна основа может соответствовать разным словам;
- недообобщение: часть форм не будет найдена;
- OR-запрос может возвращать шумные записи;
- BM25 threshold может быть нестабильным на коротких запросах;
- частые основы могут затоплять выдачу;
- латиница/кириллица/цифры/дефисы могут обрабатываться по-разному.

### Что предлагаю

Калибровка `search_score_threshold` — правильно, что она обязательна. Но я бы усилил требования:

1. Зафиксировать калибровочный корпус:
   - 20–50 реальных реплик;
   - ожидаемые релевантные записи;
   - ожидаемые нерелевантные записи.
2. Добавить метрики хотя бы на уровне приёмки:
   - precision@k;
   - recall на пилотном наборе;
   - доля пустых выдач на содержательных запросах;
   - доля возвратов на служебных запросах.
3. Ограничить количество терминов в запросе, не только длину `max_search_query`.
   Например:
   ```text
   max_search_terms = 8
   ```
   Иначе длинная реплика даст огромный OR-запрос.
4. Сделать список окончаний конфигурируемым или хотя бы вынесенным в отдельный модуль с тестами. В ТЗ он назван константой в коде — это нормально, но для калибровки лучше иметь возможность быстро править без переписывания логики.
5. Добавить тесты на инъекцию FTS5-синтаксиса:
   - `NEAR`;
   - `OR`;
   - `AND`;
   - `NOT`;
   - кавычки;
   - `*`;
   - `^`;
   - `{}`;
   - `:`;
   - переносы строк;
   - Unicode-управляющие символы.
6. Явно проверить, что запрос строится только из слов, прошедших нормализацию, и пользовательский текст не попадает в SQL/FTS5 напрямую.

Для v1 это допустимо. Но надо принимать как данность: lexical search будет иногда шуметь. Поэтому лимиты `max_return_records` и `max_return_chars` критичны.

## 3.3. Правило уплотнения 2 может преждевременно снимать полезные записи из-за слабого поиска

Правило 2:

```text
usage_count = 0
AND возраст > compaction_unused_age
AND timestamp > rebuilt_at
```

Логика понятна: если запись никогда не использовалась поиском, она кандидат на снятие.

Но в агентной системе с лексическим поиском `usage_count = 0` не означает «не важно». Это может означать:

- поиск не нашёл запись из-за морфологии;
- запрос был короткий;
- порог слишком высокий;
- запись относится к другому проекту;
- запись ещё не попала в релевантный контекст;
- пользователь не задавал похожие вопросы.

### Риск

Можно случайно снять из поиска полезные старые записи только потому, что lexical search слабый.

### Что предлагаю

Для v1 я бы сделал одно из:

1. Выключить правило 2 по умолчанию.
2. Сделать правило 2 конфигурируемым:
   ```text
   compaction_rule2_enabled = false
   ```
3. Увеличить `compaction_unused_age` значительно, например 90–180 дней.
4. Учитывать использование не только Search, но и Digest/Return, хотя ТЗ явно говорит, что счётчик увеличивает только Поиск. Если менять — надо менять ТЗ.
5. Перед включением COMPACTION в рабочем режиме провести приёмку на реальном журнале и проверить, сколько полезных записей будет снято.

Мне кажется, для MiniMem-1 более безопасный default:

```text
COMPACTION=OFF
```

или

```text
COMPACTION=ON, но rule2=OFF
```

Правила 1 и 3 более безопасны: возраст и точные дубликаты.

## 3.4. Вставка памяти в сообщение пользователя требует более строгой нейтрализации delimiter-инъекций

Формат вставки §13 хороший: память обозначена как данные, есть начало и конец блока, есть метаданные.

Но если в сохранённом тексте встречается строка:

```text
=== КОНЕЦ ДАННЫХ ПАМЯТИ ===
```

или похожая, она может сломать границы блока. Также возможны управляющие символы, zero-width characters, markdown-заголовки, имитация системных инструкций.

Полноценная prompt injection защита в v1 не требуется — это правильно. Но базовая нейтрализация нужна.

### Что предлагаю

При вставке памяти:

1. Экранировать или заменять точные строки-делимитеры:
   - `=== НАЧАЛО ДАННЫХ ПАМЯТИ ===`
   - `=== КОНЕЦ ДАННЫХ ПАМЯТИ ===`
2. Удалять или заменять управляющие Unicode-символы:
   - zero-width space;
   - BOM внутри текста;
   - control chars, кроме `\n`, `\t`;
   - возможные terminal escape sequences.
3. Ограничивать длину каждой записи и суммарную длину.
4. Не включать в вставку сырые HTML-комментарии, если они могут повлиять на downstream-обработку.
5. Добавить тест:
   - запись содержит конец блока памяти;
   - запись содержит `### User` / `### Assistant`;
   - запись содержит FTS5-операторы;
   - запись содержит markdown-заголовки;
   - запись содержит Unicode control characters.

Это не сделает систему неуязвимой, но повысит устойчивость.

## 3.5. Redaction: нужны более явные шаблоны и тесты на ложные срабатывания

Раздел 7 задаёт минимальные категории:

- API keys;
- access tokens;
- Bearer;
- пароли;
- connection strings;
- административные секреты.

Это правильно по направлению, но слишком общо для реализации только стандартной библиотекой.

### Риски

- ложные срабатывания: удалят обычный текст, похожий на ключ;
- ложные пропуски: современные токены могут быть многострочными, base64, JWT, PEM, SSH, AWS, GitHub, Slack, Google, Azure, database URLs;
- regex catastrophic backtracking;
- секреты в логах;
- секреты в имени проекта/сессии/пути.

### Что предлагаю

Добавить в ТЗ конкретный встроенный набор шаблонов, хотя бы примерный:

- OpenAI-style keys;
- Anthropic keys;
- AWS access key id / secret access key;
- GitHub token `ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`;
- Slack tokens;
- Google API keys;
- JWT;
- PEM private keys;
- connection strings вида `postgres://user:pass@host`;
- `Authorization: Bearer ...`;
- `password=...`, `passwd=...`, `secret=...`, `token=...`;
- длинные base64-строки в контексте ключей, но осторожно.

Также:

1. Шаблоны должны быть конфигурируемыми.
2. Логировать только категорию и количество замен, не фрагменты секрета.
3. Добавить тесты на ложные срабатывания:
   - обычный текст со словом `password` без значения;
   - URL без пароля;
   - хеш;
   - UUID;
   - код с переменными.
4. Добавить тесты на многострочные секреты.
5. Использовать линейные паттерны, без вложенных квантификаторов.

Для v1 можно не делать идеальную DLP, но надо сделать предсказуемую.

## 3.6. Выбор «последнего дайджеста» по файловой системе может быть ненадёжным

Return на первом ходе читает последний по времени файл дайджеста проекта, кроме текущего сессии.

Но как определять «последний по времени»?

- mtime файла?
- имя файла?
- дата в заголовке дайджеста?
- порядок записи в каталоге?

На Windows mtime может быть ненадёжен из-за копирования, синхронизации, restore, антивируса, облачных клиентов.

### Что предлагаю

Нужен детерминированный порядок.

Варианты:

1. Имя файла должно содержать сортируемый timestamp:
   ```text
   <session_id>.md
   ```
   недостаточно, если `session_id` не сортируется хронологически.

   Лучше:
   ```text
   2026-09-22T07-31-02+04-00__<sanitized_session_id>.md
   ```
   Но это усложняет соответствие `session_id`.

2. Парсить заголовок дайджеста:
   ```text
   - Создан: ...
   - Дата: ...
   ```
   и выбирать максимальный по `Создан`.

3. Хранить мини-манифест дайджестов в SQLite, но дайджест не должен становиться источником истины. Манифест может быть производным кэшем.

Для v1 я бы рекомендовал:

- имя файла остаётся `<session_id>.md`;
- при выборе последнего дайджеста парсится поле `Создан` из заголовка;
- если поле отсутствует или повреждено — использовать mtime как fallback и логировать warning;
- `session_id` sanitize для filesystem-safe имени.

Также нужно явно определить sanitize:

- запрет `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`;
- ограничение длины;
- стабильное преобразование.

## 3.7. Определение проекта нужно детализировать для Windows

Проект определяется по `cwd` и `path_prefix → project`.

Но на Windows есть нюансы:

- регистронезависимость путей;
- alternate data streams не важны, но normalize path нужен;
- symlink / junction;
- короткие имена 8.3;
- UNC-пути;
- trailing backslash;
- разные буквы диска;
- отсутствующий `cwd`.

### Что предлагаю

Явно зафиксировать:

1. Путь нормализуется через `os.path.realpath` или `Path.resolve(strict=False)`.
2. Сравнение префиксов case-insensitive на Windows.
3. Используется самое длинное совпадение префикса.
4. Если `cwd` отсутствует или не читается — проект `common`.
5. Префиксы в конфиге тоже нормализуются.
6. Разделитель трактуется независимо от слэша.

Пример:

```text
C:\Projects\MEM_Hermes → mem_hermes
C:\Projects\MEM_Hermes\minimem → mem_hermes
```

Должно работать стабильно.

## 3.8. Параллельность и блокировка журнала на Windows требуют явной реализации

ТЗ говорит:

> append под межпроцессной блокировкой; в один момент один писатель на дневной файл.

Но не говорит, как именно.

В Python standard library на Windows это нетривиально. Варианты:

- `msvcrt.locking`;
- advisory lock file;
- `portalocker` — но это внешняя зависимость, запрещена;
- атомарный `O_APPEND` — на Windows гарантии слабее;
- named mutex — через `ctypes`, сложно.

### Что предлагаю

Нужно выбрать и зафиксировать механизм.

Для stdlib-only я бы рассмотрел:

1. Отдельный lock-файл на каждый дневной журнал:
   ```text
   2026-09-25.md.lock
   ```
2. Попытка эксклюзивного создания через `os.open(..., O_CREAT | O_EXCL)`.
3. Таймаут и retry.
4. Удаление lock при нормальном завершении.
5. Обработка stale lock: если lock старше N секунд и процесс умер — возможно, удалять, но это рискованно.

Либо использовать `msvcrt.locking` на самом файле журнала. Нужно прототипировать на целевой машине.

Главное: в ТЗ должен быть конкретный алгоритм, иначе разработчики сделают по-разному.

Это прямо следует из раздела X, но в плане это не выражено как операционная процедура.

# 5. Чего не хватает в ТЗ как в архитектурном документе

## 5.1. Нет явной модели данных

Есть описание файлов и SQLite, но нет нормальной ER-схемы. Для системы с журналом, индексом, сессиями, suppression, usage counters, cursors, digest status нужна хотя бы табличная схема.

Я бы добавил раздел «Схема служебного слоя» с таблицами:

- `memory_fts`
- `usage_counters`
- `suppressed_records`
- `sessions`
- `session_returns`
- `journal_cursors`
- `meta`

И полями, индексами, ограничениями.

---

## 5.2. Нет state diagram для сессии

Нужна диаграмма состояний:

```text
new session
  -> first turn
  -> catch-up pending?
  -> compaction previous?
  -> digest previous?
  -> return digest?
  -> normal turns
  -> context compaction detected?
  -> digest current?
  -> return current?
  -> session end
  -> compaction current?
  -> digest current?
  -> completed
```

Это уберёт неоднозначности в Этапе 4 и 7.

---

## 5.3. Нет политики обработки повреждённых данных

Частично есть:

- повреждённая запись журнала пропускается;
- `verify` сообщает;
- `rebuild-index` пересчитывает.

Но не хватает:

- что делать с повреждённым дайджестом;
- что делать с повреждённым session state;
- что делать с несоответствием `journal_offset`;
- что делать с duplicate `event_id` в журнале;
- что делать с записью без `content_hash`;
- что делать с неизвестным значением `truncated`;
- что делать с файлом журнала, который уменьшился;
- что делать, если SQLite future schema version;
- что делать, если config нечитаемый.

Для источника истины это важно.

---

## 5.4. Нет чёткой границы «память vs контекст Hermes»

MiniMem вставляет память в сообщение пользователя. Это правильно, но нужно явно зафиксировать:

- память не является инструкцией;
- память может содержать враждебный текст;
- Hermes/модель должна трактовать её как данные;
- MiniMem не гарантирует защиту от prompt injection;
- базовая нейтрализация делимитеров обязательна.

Сейчас это есть частично, но я бы сделал более явным security note.

# 7. Архитектурный вердикт

Как системный архитектор агентных систем, я бы сказал так:

## Сильная сторона проекта

MiniMem-1 правильно понимает, что память агента — это не «база знаний с AI», а критическая runtime-подсистема, которая должна:

- не ломать агента;
- быть восстанавливаемой;
- быть аудируемой;
- быть детерминированной;
- не зависеть от модели;
- не становиться вторым источником истины;
- иметь чёткие лимиты и таймауты.

Это редкая и здоровая позиция. Многие проекты памяти агентов сразу начинают с embeddings, summarization LLM, graph memory, semantic deduplication и фоном, а потом тонут в невоспроизводимости. Здесь этого нет, и это хорошо.

## Главная риск-область

Главные риски не в концепции, а в операционной детализации:

- идентичность события;
- целостность журнала при сбоях;
- производительность индексатора;
- catch-up в жёстком таймауте;
- режимы;
- ложные дубликаты из-за truncation;
- слабая русская морфология;
- преждевременное уплотнение по usage_count;
- prompt injection через вставку памяти.

## Итоговая рекомендация

Я бы рекомендовал:

1. **Не начинать Этап 1**, пока не исправлены P0-противоречия в формате записи и SQLite-схеме.
2. **Начинать Этап 0 можно**, потому что каркас, config, paths, log, project не зависят от большинства спорных деталей.
3. **После правок ТЗ** формат журнала считать стабильным только с учётом:
   - stable event_id;
   - pre-truncation content_hash;
   - nested begin parsing rule;
   - atomic append;
   - session_id/turn в индексе.
4. **В рабочем режиме сначала включать только CAPTURE**. Return, Search и Compaction включать отдельно после приёмки каждого модуля.
5. **Compaction rule 2 держать выключенным** до накопления реальной статистики и калибровки поиска.

Если эти правки внести, MiniMem-1 станет очень крепкой минимальной памятью для Hermes. Если оставить как есть, высок риск, что первая же эксплуатация покажет проблемы с повторами ходов, таймаутами индексатора, ложными дубликатами и непредсказуемым возвратом дайджестов.
