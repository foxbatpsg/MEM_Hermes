# Как смотреть, что память работает

Инструкция для владельца. Не требует правок кода, всё работает на текущей
установленной системе: хуки зарегистрированы, режимы включены, запрещать
ничего не нужно.

## Коротко

Работать в Hermes как обычно. Память пишет журнал сама. Чтобы посмотреть,
что именно она записала и как отдаёт, — четыре команды из папки `minimem`.

## Команда 1. Общая сводка за день

```shell
cd C:\Projects\MEM_Hermes\minimem
python -B minimem.py stats
```

Это главный отчёт. Он отвечает на вопрос «память вообще работает».

Что должно быть в норме:

| Строка | Норма | Что означает |
|---|---|---|
| `захват: turns_seen … turns_captured` | captured растёт | ходы пишутся в журнал |
| `turns_skipped` | 0 | ни один рабочий ход не потерян |
| `body withheld` | 0 | секреты не вызвали отказа записи |
| `поиск: запусков` | растёт | поиск по реплике срабатывает |
| `ошибок, таймаутов` | 0 | падений нет |
| `задержки хуков: p50 … max` | единицы миллисекунд | хуки не мешают Hermes |
| `пустых событий` | бывает | служебные прогоны Hermes без реплики и ответа |

Что означать «плохо»:

- `turns_skipped` больше нуля — часть рабочих ходов **действительно не записана**
  (отказ журнала: занятый диск, непрошенная блокировка). Это единственное
  значение, за которым стоит потеря данных. Разбираться надо сразу.
- `body withheld` больше нуля — реплисты с секретами целиком отброшены.
- `таймаутов` больше нуля — хук не уложился в лимит, ход мог потерять память.
- `повреждённых записей` больше нуля — в журнале битые записи.

Про два счётчика, которые часто путают:

- `turns_skipped` — **потеря данных**. Показывает ходы, которые Hermes передал,
  а MiniMem не смог записать. Должен быть нулём.
- `пустых событий` — **не потеря**. Hermes иногда шлёт событие вовсе без
  реплики и без ответа: это служебный прогон, а не ход. Записывать такое в
  журнал незачем, но и тревожиться по нему не нужно.

Разделение сделано 2026-09-26 (RB-16). До этого пустые события попадали в
`turns_skipped`, а настоящие отказы записи в него не попадали вовсе — то есть
счётчик показывал ровно обратное. В записях лога, сделанных до правки, старые
значения сохранены как есть: лог есть источник истины и не переписывается.

## Команда 2. Что именно записано

```shell
python -B minimem.py verify
```

Последняя строка ответа — `итог: без проблем`. Это проверка целостности:
журнал против индекса, дубликаты, повреждения, курсоры, дайджесты.

Если `итог: проблемы`, дальше по строкам будет написано, что именно. Первую
же строку с `проблема:` нужно прислать — по ней разбираться проще всего.

Проверять имеет смысл, когда что-то ведёт себя странно. Раз в день не нужно.

## Команда 3. Поиск памяти глазами

Главная команда для понимания качества. Показывает, что именно память
достаёт из прошлого по вашей реплике.

```shell
python -B minimem.py search "настройка бэкапа журнала" --explain
```

Читать вывод:

- `основы:` — слова, по которым шёл поиск. Обрезаны до корня: `бэкап` ищется
  как `бэкап*`. Если видите обрезку, слова подобраны неудачно.
- `режим запроса: all` — сначала строгое совпадение всех слов.
  `any` — не нашлось, идёт поиск по любому из слов.
- `порог: … (relative>=… absolute>=… rule=max)` — граница отсева. Сейчас
  `absolute` = 1.0, это `search_score_threshold`.
- строки со `score=` — найденные записи, от лучшей к худшей.
- `— выдаётся` — запись попадёт в ответ. `— отсев: below_threshold` — нашлась,
  но не прошла порог.

Живой пример на 2026-09-26:

```
попаданий: 2
  e_4f80c767… score=2.5899 — выдаётся
  e_f9018e89… score=0.8069 — отсев: below_threshold
```

Это работает как задумано: вторая запись действительно про бэкап, но её
оценка ниже порога 1.0, поэтому в ответ она не попала.

**Как пользоваться для калибровки.** Это и есть материал, которого не
хватало. Пока оболочка наполнена установочными прогонами, порог трогать
рано. Набирайте содержательные задачи, потом смотрите сюда: если много
`отсев: below_threshold` у записей, которые вы считаете подходящими — порог
занижен. Если в выдачу лезет нерелевантное — завышен.

Признак, что пора смотреть: 20–30 содержательных записей и десяток
разных запросов с разбросом оценок. Тогда и решается вопрос с порогом.

## Команда 4. Состояние хранилища

```shell
python -B minimem.py status
```

Показывает путь журнала, число файлов, состояние SQLite, размер индекса,
активные режимы. Нужна, если кажется, что память «отвалилась».

Главное — `конфигурация: валидна` и `ошибка последнего запуска: нет`.

## Чего ожидать на практике

В первые дни работы вы не заметите разницы. Это нормально и так задумано:
память — не подсказка, а фон. Нулевой результат не означает поломку, означает
мало материала.

Заметный эффект появляется позже: на второй-третьей сессии в новом проекте
первый ход начинается с выжимки прошлой работы. Если такое произошло и
выжимка к месту — память работает.

## Три команды, которые стоит выполнять регулярно

| Когда | Команда | Повод беспокоиться |
|---|---|---|
| Раз в неделю | `stats` | `turns_skipped`, `таймаутов`, `body withheld` не нули |
| Когда ищете выжимку | `search "…" --explain` | сплошной `отсев` у подходящих записей |
| Когда что-то сломалось | `verify` | не «без проблем» |

## Чего делать не нужно

- Не править журнал вручную. Это единственный источник истины.
- Не трогать пороги в `minimem/config.json` без причины — причина сейчас не
  накоплена.
- Не запускать `rebuild-index` просто так. Он безопасен, но лишний раз
  пересобирает индекс и выбивает из отчёта счётчики уплотнения.
