# MiniMem-1 — архитектура реализации

Документ для агентов, которые будут дорабатывать систему. Описывает **как
устроено то, что написано**, а не что требуется. Норматив — «Docs/MiniMem-1 -
Техническое задание v1.7»; при расхождении документа и кода прав вносит
владелец, агент фиксирует расхождение в `INDEX.md`.

## 0. Три вещи, которые нужно знать до правки

1. **Журнал — источник истины.** `<memory_root>/<project>/memory/YYYY-MM-DD.md`,
   обычный Markdown. SQLite (`minimem.db`), дайджесты, логи и отчёты — всё
   производное и пересобирается. Поэтому правка почти никогда не должна
   трогать формат журнала: сломать его значит потерять память.
2. **Никаких внешних зависимостей.** Только стандартная библиотека Python.
   Хуки запускаются интерпретатором из venv Hermes, туда нельзя ставить
   пакеты. Следствие: FTS5 берётся из системного SQLite, морфологической
   библиотеки нет, стемминг свой.
3. **Хук не имеет права упасть.** Любой отказ перехватывается на границе
   `hooks/*.py`, пишется в лог и возвращается кодом 0 с пустым объектом в
   stdout. Hermes не должен заметить проблемы MiniMem.

## 1. Слои и их зависимости

Зависимости идут строго вниз. Обратных ссылок нет — кроме `session`, который
знает про `insert`.

```
hooks/                граница с Hermes: stdin -> stdout, весь отказ ловится здесь
  |
  +-- mm/capture.py      Захват: ход -> запись журнала      (§3.1, §5, §6, §7, П-01, П-02, П-08, П-09, П-18)
  +-- mm/ret.py          Возврат: дайджест -> блок в ответ (§3.2, §11, П-04, П-07)
  +-- mm/search.py       Поиск: реплика -> записи памяти    (§3.3, §9, §12, П-11)
  +-- mm/compaction.py   Уплотнение: снятие с поиска       (§3.5, §15, §16)
  +-- mm/digest.py       Дайджест: выжимка сессии          (§3.4, §14)
  +-- mm/catchup.py      Catch-up: подготовка прошлой сессии (§18.1)
  +-- mm/indexer.py      Индексатор: журнал -> SQLite      (§3.6, §9.2)
  +-- mm/doctor.py       Диагностика (вне потока хука)     (§21.1, П-06, П-19)
  +-- mm/stats.py        Отчёт по логу (вне потока хука)  (§21.3, П-10)
  |
  +-- mm/session.py      Состояние сессии, разбор события  (§17, §26.2)
  +-- mm/journal.py      Атомарная запись и разбор журнала (§4.1, §4.4, §4.5, П-13)
  +-- mm/canonical.py    Канонизация, event_id, сериализация (§4.4, §5)
  +-- mm/redaction.py    Замена секретов                   (§7, П-08)
  +-- mm/insert.py       Формат блока и санитизация        (§13, §13.1, П-01)
  |
  +-- mm/store.py        Схема и запросы SQLite            (§4.2, §9.1)
  +-- mm/project.py      Определение проекта               (§8, П-16)
  +-- mm/paths.py        Пути хранилища                    (§4.1)
  +-- mm/config.py       Загрузка и инварианты конфигурации (§20, П-14)
  +-- mm/log.py          Структурированный лог             (§22, П-10)
  +-- mm/query.py        Построение FTS-запроса            (§12, §12.1)
  +-- mm/reproject.py    Перепривязка к проектам (CLI)     (§8 п. 10, §21.4)
```

**Инвариант, который нельзя нарушать:** модуль никогда не читает журнал,
если он не Захват или Индексатор. Дайджест, Поиск, Возврат, Уплотнение и
Catch-up берут данные только из SQLite и файлов дайджестов. Причина
архитектурная (§2): журнал пишется атомарно, SQLite можно читать транзакцией
под блокировкой, а чтение журнала конкурировало бы с записью.

**Второй инвариант:** Индексатор никогда не пишет в журнал и не получает
данных от Захвата. Это два независимых запуска: Захват дописал запись —
Индексатор её прочитал (§2).


## 2. Почему модулей именно столько

Разделение не стилистическое, оно определяет, что можно менять безопасно.

| Модуль | Что делает | Почему отдельно |
|---|---|---|
| `journal.py` | append под `msvcrt.locking`, разбор дневного файла конечным автоматом | Единственное место, где пишется журнал. Формат записи и порядок маркеров живут здесь, ломать его опасно |
| `canonical.py` | `content_hash`, `event_id`, сериализация записи | Идентичность хода вычисляется только здесь; `event_id` не зависит от содержимого (MM-101) |
| `redaction.py` | линейный набор regex-шаблонов, placeholder'ы | Детерминированность: одинаковый секрет всегда даёт одинаковый placeholder и `content_hash` (MM-107) |
| `insert.py` | блок памяти, делимитеры, санитизация | Граница вставки в контекст LLM; здесь же удаление блока из реплики (П-01) |
| `store.py` | DDL и запросы SQLite | Единственный владелец схемы; остальные модули SQL не пишут |
| `indexer.py` | инкрементальное чтение журнала, FTS5 | Курсоры, инкрементальность и восстановимость — его ответственность |
| `session.py` | состояние сессии, детекция сжатия | Мест, где нужна память между ходами, — `meta`, а не `sessions` (§17 не покрывает эти поля) |
| `doctor.py`, `stats.py` | вне потока хука | Оба только читают; их можно вызывать в любой момент, не рискуя рабочим ходом |

Объём кода на 2026-09-26: `mm/` — около 6300 строк в 20 модулях, `hooks/` —
550 строк в трёх скриптах, `minimem.py` (CLI) — около 730 строк, тесты —
около 7500 строк.

## 3. Поток хода

### `post_llm_call` — Захват

Порядок задан нормой и в коде не переставляется (`mm/capture.py`):

1. Проверка `mode_capture`; выключен — `capture_disabled`, выход.
2. Пустое событие (нет ни реплики, ни ответа) — `capture_invalid_event`
   со счётчиком `empty_events`. Это отсутствие хода, а не потеря (§3.1 п. 14).
3. Удаление блока памяти из реплики (П-01) — операция `insert_stripped`.
4. Определение проекта по `cwd` (§8).
5. Redaction обеих частей; сбой или таймаут → `body_status=withheld` (П-08).
6. `content_hash` по полному содержимому **до** обрезки (§5).
7. Обрезка по `max_user_text` / `max_assistant_text` / `max_memory_record`.
8. `event_id` по ключу `project + session_id + task_id + turn` (§5).
9. Сериализация записи; при конфликте `event_id` с другим хешем — новая
   ревизия (§5.1, П-02).
10. Атомарный append под блокировкой.
11. Обновление гарда идемпотентности — best-effort.

**Пути отказа считают потерю честно.** `journal_append_failed` и
`journal_lock_timeout` пишут `turns_captured: 0, turns_skipped: 1`. Это
не украшение: до правки RB-16 они писали `captured: 1`, и критерий §25 п. 27
не мог увидеть потерю хода. Не возвращать счётчики к «по умолчанию 1».

**`capture_idempotency_guard_unavailable` — не потеря.** При недоступном
SQLite запись в журнал всё равно выполняется (§5.1, гард best-effort).

Затем в том же хуке, но **отдельным запуском**, Индексатор читает журнал.
Захват данных Индексатору не передаёт.

### `pre_llm_call` — состояние, Возврат, Поиск

1. Состояние сессии и метрики истории **без блоков памяти** — иначе
   измерение искажалось бы памятью, которую сами же вставили (MM-109).
2. Детекция сжатия контекста по точкам отсчёта (§11, П-04).
3. Catch-up, если `mode_return` или `mode_compaction` (§18.1).
4. Возврат при `mode_return`: дайджест прошлой сессии на первом ходе, своей
   — на ходе сжатия.
5. Поиск при `mode_search`, если Возврат ничего не вставил.

### `on_session_end` — Уплотнение и Дайджест

Уплотнение, затем дайджест. Отказ одного шага не отменяет другой: дайджест
создаётся и при недоступном уплотнении.

## 4. Ключевые решения, которые легко сломать

### Блок памяти вставляется один раз

`insert.strip_memory_block` ищет **последний** оригинальный `END_DELIMITER`
после вводной строки, и только если его нет — первый sanitized-вариант.
Почему так: sanitized-делимитер появляется ровно там, где санитизация
заменила разделитель в содержимом. Поиск «первого совпадения любого» обрывал
блок по содержимому, и `hist_msgs`/`hist_chars` мерили остаток блока вместо
текста пользователя — это ломало детекцию сжатия (MM-127).

### Границы поиска строятся кодом

`query.py` усекает русские слова по фиксированному списку окончаний. Это не
стеммер: он ошибается, но даёт recall — «память» находит «памяти». Текст
пользователя в FTS-запрос не попадает: операторы FTS5 нейтрализованы самой
конструкцией `"основа"*`. Список окончаний менять можно, принцип — нельзя без
новой приёмки.

### Пороги поиска — `max`, а не выбор

`search.plan` берёт `max(search_score_threshold, top_score *
search_score_ratio)`. Обе величины нужны: абсолютная отсекает мусор, доля
не даёт выкинуть хорошие записи, когда всё выдалось слабым. Калибруются по
данным `stats` (RB-05), не на глаз.

### Состояние сессии лежит в `meta`, не в `sessions`

Схема `sessions` из §9.1 не содержит `max_msgs`, `max_chars` и счётчиков
вставок. Менять нормативную схему нельзя, поэтому состояние хранится в
таблице `meta` под ключом `session_state:<project>/<session_id>`. Прецедент
служебных ключей в `meta` есть (`damaged:`, П-13; `sender:`, П-18).

### Дата в заголовке записи — момент захвата

`render_record` пишет `## <timestamp> · turn <n>`. Индексатор берёт время отсюда
и нормализует в UTC. Отсюда же `compaction_age` и выбор дайджеста по «Последнему
ходу».

## 5. Хранилище

```
<memory_root>/
  <project>/memory/YYYY-MM-DD.md      журнал — источник истины
  <project>/memory/digest/<file>.md   дайджесты (производное)
  minimem.db                           служебный слой (производное)
  logs/minimem.log                     технический лог (производное)
  backups/re-project-<метка>/          копия журнала перед re-project
```

Схема SQLite (§9.1): `meta`, `capture_guard`, `memory_fts` (FTS5),
`memory_meta`, `usage_counters`, `suppressed_records`, `sessions`,
`session_returns`, `journal_cursors`. `SCHEMA_VERSION = 2`.

Снятие с поиска — только строка в `suppressed_records`. Записи из журнала не
удаляются никогда (§15). Правила 1 и 3 воспроизводятся после `rebuild-index`,
правило 2 — нет, оно зависит от `usage_count` (§16).

## 6. Конфигурация

`config.json` рядом с кодом. Ключи, отсутствующие в файле, берутся из
`DEFAULTS` в `mm/config.py` — там единственный источник правды по умолчаниям.

Три группы:

- **пути** — `memory_root`, `sqlite_filename`, `log_filename`. Не входят в
  `config_hash`.
- **режимы** — `mode_capture`, `mode_return`, `mode_search`,
  `mode_compaction`, `compaction_rule2_enabled`. Переключение не требует
  `rebuild-index` (MM-55).
- **поведенческие параметры** — лимиты, пороги, таймауты. Входят в
  `config_hash` (§20, П-14).

`config_hash` — первые 16 hex sha256 от поведенческих параметров. Правка
параметра меняет хеш и **не** меняет существующий журнал (MM-151).

Нарушение инварианта не останавливает работу: ключ возвращается к значению по
умолчанию, проблема попадает в `Config.issues` и пишется в лог как
`config_invalid` (§20 п. 4).


## 7. Как вносить правку

1. Прочитать соответствующий раздел ТЗ. Правка без нормы — сначала запись
   в `INDEX.md`, потом код.
2. Найти модуль по таблице раздела 2. Сомневаешься — искать в docstring
   ссылку на раздел ТЗ: она проставлена в каждом модуле.
3. Написать тест **до** правки кода, с номером из §23 в docstring
   (`"""MM-NNN. Что проверяем."""`). Номер обязателен: по нему работает
   генератор отчёта `tests/acceptance_v1.6.md`.
4. Внести правку. Не трогать: формат записи журнала, `event_id`,
   последовательность захвата, изоляцию ошибок на границе хуков.
5. Прогнать проверки (раздел 9).
6. Записать в `INDEX.md` в раздел решений: что, зачем, основание.
7. Если затронуты номера §23 — пересобрать отчёт приёмки.

## 8. Типичные ошибки при доработке

| Ошибка | Почему это ломает |
|---|---|
| Прочитать журнал из дайджеста/поиска | Гонка с записью, блокировки, либо потеря инкрементальности (§9.2) |
| Передать данные из Захвата в Индексатор | Нарушение §2: Индексатор должен быть восстановим из журнала |
| Изменить формат записи без правки `journal.py` | Записи перестанут разбираться; при `rebuild-index` это тихая потеря индекса |
| Посчитать событие как захваченный ход «по умолчанию» | Возвращается дефект RB-16: отчёт покажет успех там, где ход потерян |
| Сделать хук исключительным | Hermes увидит ошибку; §19.2 запрещает |
| Ослабить проверку ради PASS | §25 п. 12 прямо запрещает; единственный способ убрать проверку — статус «снят» с причиной |
| Взять примерные числа в отчёт приёмки | Отчёт не выдумывается: номера из `required_tests.txt`, статусы из прогона |
| Считать показатели по синтетическому логу | Приём `StatsCoverageTests` существует именно потому, что так прошли два дефекта |

## 9. Проверки после правки

Из `minimem/`:

```shell
python -B -m unittest discover -s tests
```

Из корня:

```shell
python -B -m unittest discover -s tests -p "test_*.py"
python -B -m unittest discover -s scripts -p "test_*.py"
python -B scripts/validate_index.py --strict
python -B scripts/build_refs_registry.py --check
```

Затронут отчёт приёмки — пересобрать:

```shell
python -B minimem/tools/build_acceptance_report.py
```

Полный порядок проверки — в `AGENTS.md`. Рабочий конфиг и рабочее хранилище
при проверках не используются: тесты работают на временных каталогах.
