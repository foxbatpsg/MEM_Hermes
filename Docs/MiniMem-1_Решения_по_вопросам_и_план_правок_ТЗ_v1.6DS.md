# MiniMem-1 — Закрытие вопросов Плана правок ТЗ v1.6 и план внесения правок

Основание: «MiniMem-1 - Техническое задание v1.6», «MiniMem-1 - План правок ТЗ v1.6», «MiniMem-1 - Реестр доработок после эксплуатации».
Обозначения: В-NN — закрытый вопрос Плана правок; П-NN — правка из Плана правок; MM-NN — номер приёмочного теста; RB-NN — запись реестра доработок.
Соответствие нумерации: MM-NN = номер NN в §23 ТЗ (в §23 тесты 51–115 записаны с префиксом MM, тесты 1–50 — без префикса; в `tests/required_tests.txt` номера записаны без префикса).
Решения приняты в роли системного архитектора агентных систем. Обоснования не выносятся.

Итог по плану правок:

- Приняты все П-01…П-18. Отклонены: вариант П-02 п.5 (производные ключи ordinal вместо ревизий) и вариант П-05 п.2 (санитизация файла дайджеста на диске).
- Блокирующими первый релиз остаются П-01, П-02, П-03, П-04, П-05, П-06, П-10. Порядок внесения — раздел 2 настоящего документа.
- Новых тестов: MM-116…MM-164. Перенумерованы: тесты П-16 с MM-155…MM-157 на MM-162…MM-164 (устранение дублей номеров).
- Изменены статусы: MM-112 — «снят (дубль MM-96)». Переформулированы: MM-30, MM-45, MM-61, MM-82, MM-90, MM-91, MM-92, MM-100.
- Реестр доработок: RB-03, RB-07 закрываются, RB-09 закрывается частично, RB-06 переформулируется, RB-01, RB-02, RB-04, RB-05, RB-08, RB-10, RB-11 остаются «Кандидат» с порогами из раздела 5.
- Правки вносятся в ТЗ как редакция v1.6.1; план правок приводится в соответствие (разделы 4.2 настоящего документа).

## 1. Решения по вопросам (В-01 … В-22)

**В-01. Что считать репликой пользователя в журнале, если Hermes вернул её с вставленным блоком памяти (П-01).**
Решение: `user_utterance` в журнале — всегда чистый текст пользователя; блок MiniMem удаляется до redaction; удаляются вводная строка «Ниже приведены данные из памяти…», блок от `=== НАЧАЛО ДАННЫХ ПАМЯТИ ===` до первого `=== КОНЕЦ ДАННЫХ ПАМЯТИ ===`, а также sanitized-варианты делимитеров; `assistant_answer` не изменяется; `truncated` не изменяется фактом удаления; `content_hash` считается по чистой реплике.
Где: §3.1 шаг 2а, §10 шаг 2а, §5, §13.1 (п.1, новые п.6 и п.7), §17, §22.
Проверка: MM-116, MM-117, MM-118.

**В-02. Блок сохранён или отброшен, если найден только один делимитер (П-01 п.5).**
Решение: блок признаётся блоком только при обеих границах; при одной границе текст сохраняется как есть, пишется `insert_strip_incomplete`.
Где: §13.1 (новый п.6), §17, §22.
Проверка: MM-118.

**В-03. Ревизии записи или производные ключи ordinal (П-02 п.1 против п.5).**
Решение: принят вариант с ревизиями. Поля записи: `revision` (целое, по умолчанию 1) и `supersedes` (event_id, пусто для первой ревизии). Служебный слой хранит одну строку на `event_id`; журнал хранит все ревизии и не перезаписывается. Вариант «новая запись с `event_id = hash(...ordinal)`» отклонён.
Где: §5, §5.1, §9.1, §21.
Проверка: MM-155, MM-156, MM-157.

**В-04. Какая ревизия каноническая при равных номерах ревизий (П-02).**
Решение: каноническая — ревизия с большим `revision`; при равенстве — с меньшим байтовым смещением в журнале; правило одинаково для индексатора и `rebuild-index` (заменяет правило «первая физическая запись»).
Где: §5.1, §9.2 п.10, §21 (rebuild-index), §19.5.
Проверка: MM-155, MM-156.

**В-05. Версия формата записи и состав метаданных (П-03).**
Решение: `fmt: 1` — первое поле метаданных. Порядок полей фиксирован: `fmt, project, session_id, task_id, turn, event_id, content_hash, truncated, project_path, body_status, revision, supersedes, redaction_set, turn_source, session_source, sender_id, platform`. Неизвестные строки `- key: value` после известных полей сохраняются при чтении и не делают запись повреждённой.
Где: §4.4 п.3, §5, §9.1.
Проверка: MM-119, MM-121.

**В-06. Что делать с недопустимым значением закрытого перечисления (`truncated`, `body_status`, `turn_source`).**
Решение: запись не считается повреждённой: текст читается, индексируется, недопустимое значение заменяется безопасным (`truncated: none`, `body_status: full`, `turn_source: hermes`), пишется `record_metadata_invalid`, `verify` даёт предупреждение. Из MM-100 формулировка «повреждение записи» удаляется.
Где: §4.4, §4.5.3, §22, §23 MM-100, §25.
Проверка: MM-100 (переформулирован), MM-119.

**В-07. Запись, созданная более новой версией формата (П-03 п.4).**
Решение: `fmt > 1` — запись читается как есть, индексируется, `verify` пишет `record_format_newer`; не индексируются только поля, которых нет в текущем формате.
Где: §4.4, §4.5.3, §21 (verify), §22.
Проверка: MM-120.

**В-08. Отсутствие `fmt` (П-03 п.5).**
Решение: трактуется как `fmt: 1`; при записи новых записей поле обязательно.
Где: §4.4, §5.
Проверка: MM-121.

**В-09. Единицы измерения истории и пороги сжатия (П-04).**
Решение: `hist_msgs` — число сообщений `conversation_history` после удаления блоков MiniMem и отбрасывания сообщений, ставших пустыми; `hist_chars` — сумма длин текстов сообщений в символах после нормализации LF. Сжатие фиксируется, если срабатывает любая пара порогов: (`hist_msgs < max_msgs * compaction_shrink_ratio` и `max_msgs - hist_msgs >= compaction_min_drop`) либо (`hist_chars < max_chars * compaction_shrink_ratio` и `max_chars - hist_chars >= compaction_min_chars_drop`). Значения: `compaction_min_drop = 6`, `compaction_min_chars_drop = 2000`, `compaction_shrink_ratio = 0.6`.
Где: §11, §17, §20.
Проверка: MM-45 (переформулирован), MM-109, MM-122.

**В-10. Защита от ложных срабатываний сжатия (П-04 п.3–4).**
Решение: `compaction_cooldown_turns = 2`; `max_return_injections_per_session = 3`; исчерпание лимита логируется `return_injection_limit`; решение логируется целиком: `hist_msgs, hist_chars, max_msgs, max_chars, compaction_decision, threshold_applied`.
Где: §11, §17, §19.5, §20, §22.
Проверка: MM-123, MM-124, MM-125.

**В-11. Где санитизируется текст, вставляемый в контекст (П-05 п.2 — санитизация файла против санитизации вставки).**
Решение: файл дайджеста хранит исходный текст журнала без изменений; санитизация выполняется единой функцией только на вставке в контекст (`search`, дайджест при старте, дайджест при сжатии); в файле дайджеста запрещены строки, создающие вторую границу блока, они нейтрализуются только при вставке.
Где: §11, §13, §13.1, §14.
Проверка: MM-82 (расширен), MM-126, MM-127.

**В-12. Бюджеты хуков (П-06).**
Решение: `hook_deadline_ms = min(таймаут хука по config.yaml Hermes, внутренний предел) − hook_safety_margin_ms`, `hook_safety_margin_ms = 2000`. Суббюджеты: capture 0.4, indexer 0.4, catch-up ≤ min(`catch_up_budget_seconds * 1000`, 0.4 остатка), дайджест ≤ 0.3 остатка, `return_min_budget_ms = 300` не отдаётся catch-up. Приоритет: вставка памяти важнее catch-up; при нехватке остатка — `pending_catch_up`, Возврат выполняется. `deadline_remaining_ms` обязательно заполняется всеми модулями.
Где: §10, §11, §18.1, §19.1, §20, §22.
Проверка: MM-128, MM-129, MM-130.

**В-13. Ключ выбора последнего дайджеста (П-07).**
Решение: нормативным является поле заголовка «Последний ход: \<ISO-8601 UTC\>»; «Создан» — информационное; `rebuild-digest` не меняет «Последний ход»; tie-break — меньшее имя файла; fallback на mtime только при нечитаемом «Последнем ходу» с логом `digest_last_turn_fallback`. Catch-up строит дайджест той сессии, которую выберет правило Возврата.
Где: §3.2, §11.1, §14, §18.1 п.3 и п.6, §21, RB-06.
Проверка: MM-30 (переформулирован), MM-90, MM-91, MM-132, MM-133.

**В-14. Поведение при сбое redaction (П-08).**
Решение: `body_status: full | withheld`; при исключении, превышении `redaction_timeout_ms = 200` мс или нарушении UTF-8 запись сохраняется с `body_status: withheld`, тело не пишется, `truncated: none`, событие `record_body_withheld_redaction_failed`; withheld-записи не индексируются и не выбираются поиском, метаданные остаются в `memory_meta`. Текст исключений и traceback в основной лог не пишется, только `error_code`; traceback — в отдельный файл при `debug_traceback = true` и после redaction. `stdin` читается с `errors="replace"`, кодировка UTF-8 явно.
Где: §7, §7.1, §9.1, §10, §19.2, §22, §25.
Проверка: MM-134, MM-135, MM-136.

**В-15. Потеря хода без `turn_id` или `session_id` (П-09 п.2 — потерять или сохранить).**
Решение: сохранять. При отсутствии `turn_id`: `turn = "?" + первые 16 hex sha256(session_id + timestamp + content_hash)`, `turn_source: derived` (event_id считается по формуле §5 без изменений). При отсутствии `session_id`: `session_id = unknown-<YYYY-MM-DD>`, `session_source: derived`. Проект определяется по cwd как обычно, `common` — только при отсутствии cwd. Логирование: `capture_turn_derived`, `capture_session_derived`. `turns_skipped = 0` — критерий приёмки.
Где: §3.1, §5, §10, §19.5, §22, §25.
Проверка: MM-137, MM-138, MM-139.

**В-16. Контракт измеримости (П-10).**
Решение: агрегация выполняется офлайн-командой `minimem stats` по логу, без новых таблиц; обязательный нормативный список метрик — раздел 3.3 настоящего документа; поля лога поиска (`search_terms, search_query_mode, search_hits, search_returned, returned_event_ids, top5_scores, score_floor_applied, score_ratio_applied`) обязательны к заполнению. Решения по RB-01, RB-02, RB-05 принимаются только по отчёту `stats`.
Где: §12, §19.5, §21, §22, §25.
Проверка: MM-140, MM-141, MM-142.

**В-17. Построение поискового запроса и отсев (П-11).**
Решение: двухступенчатый запрос: сначала AND по основам (`"основа"*`), при пустой выдаче — релаксация до OR; фактический режим пишется в `search_query_mode: all | any`. Отсев относительный: `score >= top_score * search_score_ratio`, `search_score_ratio = 0.35`; `search_score_threshold = 0` как абсолютный пол. `usage_count` увеличивается только у фактически вставленных записей.
Где: §9, §12, §12.1, §16, §20.
Проверка: MM-143, MM-144, MM-145.

**В-18. Алгоритм имени файла дайджеста (П-12).**
Решение: каждый символ вне `[A-Za-z0-9._-]` → `_`, результат в нижний регистр, обрезка до 64 символов, добавление `--<первые 8 hex sha256(session_id)>`; итог `<safe>--<hash8>.md`; отображение хранится в `sessions.digest_file`; при коллизии — `digest_name_collision`, существующий файл не перезаписывается.
Где: §14, §9.1, §21.
Проверка: MM-92 (переформулирован), MM-146, MM-147.

**В-19. Блокировка журнала и контроль append (П-13).**
Решение: единый модуль блокировки `journal_lock` с цепочкой: Windows — `msvcrt.locking` на байтовом диапазоне, POSIX — `fcntl.flock(LOCK_EX)`, fallback — lock file стандартной библиотеки; порядок операций: lock → seek в конец → write одной записью → flush → fsync → unlock; создание нового дневного файла на POSIX сопровождается fsync каталога. После записи проверяются размер файла и наличие завершающего маркера; при несовпадении — `journal_append_unverified` и запрет продвижения курсора. Лог повреждений дедуплицируется по (файл, смещение, mtime), повторные обнаружения — счётчиком. `verify` проверяет непрерывность файла и пишет `journal_externally_modified`.
Где: §4.5.1, §4.5.2, §4.5.3, §9.2, §19.3, §21, §22, RB-07.
Проверка: MM-148, MM-149, MM-150.

**В-20. Версионирование и валидация конфигурации (П-14).**
Решение: в `meta` пишутся `config_hash` (sha256 канонизированного конфига без шаблонов redaction) и `minimem_version` при первом запуске и при изменении; при изменении поведенческих параметров — событие `config_changed` со списком ключей. Инварианты проверяются на старте: `compaction_unused_age < compaction_age`, `compaction_unused_age >= 0`, `digest_turns >= 1`, `search_score_threshold >= 0`, `search_score_ratio` в (0, 1], сумма суббюджетов ≤ `hook_deadline_ms`, `catch_up_budget_seconds * 1000` ≤ 0.4 `hook_deadline_ms`, `return_min_budget_ms` < `hook_deadline_ms`. При нарушении — безопасные значения по умолчанию и `config_invalid`.
Где: §4.2, §9.1, §19.1, §20, §20.1, §21.
Проверка: MM-151, MM-152.

**В-21. Состав обязательных тестов и организация приёмки (П-15).**
Решение: обязательные номера — 1–50, 51–68, 79–89, 101–111, 113–115, 116–164 (MM-112 снят как дубль MM-96); статусы пересматриваются при утверждении каждой редакции; отчёт приёмки — `tests/acceptance_v1.6.md` со всеми номерами 1…N и статусами, отсутствие номера = непройденная приёмка; проверку наличия обязательных номеров выполняет `tests/test_required_numbers.py`.
Где: §23 (в целом), §25 п.10–13, RB-03.
Проверка: MM-153, MM-154.

**В-22. Идентичность проекта, автора и прерванной сессии (П-16, П-17, П-18).**
Решение: в запись добавляются `project_path` (нормализованный по §8 cwd на момент захвата) и `sender_id`, `platform` (пустые допустимы); `project` в записи никогда не перезаписывается автоматически, переопределение — только командой `minimem re-project` с резервной копией журнала и пересборкой производного слоя; в `meta` хранится `project_mapping_hash`; `verify --projects` сообщает расхождение маппинга. Дайджест всегда содержит поле «Завершение: полное | прервано | сбой»; при `interrupted` или `failed` в вставку добавляется строка «предыдущая сессия прервана, выжимка неполная»; уплотнение в catch-up выполняется как обычно; событие `digest_interrupted_fallback`. Память не разделяется по пользователям: CAPTURE на многопользовательских платформах — только в доверенном контуре; смена `sender_id` в сессии логируется `sender_changed`; scope памяти `user/project/team` отнесён в §24 и Р-08.
Где: §1, §5, §8, §14, §15, §17, §18, §21, §24, §26.2.
Проверка: MM-158, MM-159, MM-160, MM-161, MM-162, MM-163, MM-164.

## 2. План внесения правок (где / на что / что проверить)

### Шаг 1. Формат записи и ключи: П-03, П-02, П-16

**П-03. Версия формата и forward-compat.**
- §4.4 п.3: заменить список порядка метаданных `project, session_id, task_id, turn, event_id, content_hash, truncated` на `fmt, project, session_id, task_id, turn, event_id, content_hash, truncated, project_path, body_status, revision, supersedes, redaction_set, turn_source, session_source, sender_id, platform`.
- §4.4: добавить пункты — «fmt: 1 — обязательное первое поле метаданных; отсутствие fmt трактуется как fmt: 1»; «неизвестные строки вида `- key: value` после известных полей сохраняются при чтении и не делают запись повреждённой»; «формат файла считается новее, если fmt > 1».
- §4.4: добавить п.15 «повреждение относится только к структуре: маркеры `<!-- mm:begin -->`/`<!-- mm:end -->`, строки `### User`/`### Assistant`, порядок секций; состав и значения метаданных повреждением не являются».
- §4.5.3: добавить ветку «недопустимое значение закрытого перечисления — не повреждение; безопасное значение + `record_metadata_invalid`» и «fmt > 1 — чтение как есть + `record_format_newer`».
- §5: добавить в список полей записи `fmt`, `project_path`, `body_status`, `revision`, `supersedes`, `redaction_set`, `turn_source`, `session_source`, `sender_id`, `platform`.
- §5: добавить правило «user_utterance в журнале — текст без вставок MiniMem» (см. П-01).
- §9.1 `memory_meta`: добавить `fmt INTEGER NOT NULL DEFAULT 1`, `body_status TEXT NOT NULL DEFAULT 'full' CHECK (body_status IN ('full','withheld'))`, `revision INTEGER NOT NULL DEFAULT 1`, `supersedes TEXT`, `project_path TEXT`, `turn_source TEXT NOT NULL DEFAULT 'hermes'`, `session_source TEXT NOT NULL DEFAULT 'hermes'`, `sender_id TEXT`, `platform TEXT`; добавить индекс `idx_meta_event_revision (event_id, revision)`.
- §21 `verify`: добавить проверки «неизвестные ключи метаданных», «fmt > поддерживаемого», «записи с `body_status: withheld`», «записи с устаревшим `redaction_set`».
- §22: в список операций добавить `record_format_newer`, `record_metadata_invalid`, `record_body_withheld_redaction_failed`.
- §23 MM-100: заменить «неизвестное значение truncated делает запись повреждённой» на «запись читается и индексируется с truncated = none, пишется `record_metadata_invalid`, verify даёт предупреждение».
- §25: заменить п.23 «Duplicate event_id обрабатывается детерминированно» на «Ревизии event_id обрабатываются детерминированно: в индексе одна актуальная ревизия».
- Проверить: MM-119, MM-120, MM-121, MM-100.

**П-02. Ревизии записи вместо отбрасывания.**
- §5.1: заменить «если event_id существует, но content_hash отличается, новая физическая запись не создаётся; событие логируется как capture_event_conflict» на «в журнал дописывается новая ревизия: `revision = предыдущая + 1`, `supersedes = event_id`; событие логируется как `capture_event_revision_added`».

### 3.3. Обязательные метрики `minimem stats` (§21, §19.5)

- Поиск: число запусков, доля пустых выдач, доля выдач в режиме `any`, среднее число основ, среднее число попаданий, распределение score (p50/p95/max), доля отсева относительным порогом, `top5_scores` по последним ходам.
- Захват: `turns_seen, turns_captured, turns_skipped, turns_derived`, `insert_stripped_count/chars`, `redaction_count`, `withheld_count`, доля `withheld`, число ревизий (`event_revision_applied`), дубли (`capture_duplicate_ignored`).
- Индексатор: отставание курсора, `cursor_reset`, `journal_record_damaged`, `journal_duplicate_event_id`, `journal_append_unverified`, `journal_externally_modified`.
- Catch-up: число запусков, `catch_up_timeout`, `catch_up_state_unavailable`, `pending_catch_up`, `catch_up_attempts`, доля необработанных предыдущих сессий.
- Дайджест: создан, пересобран, `digest_last_turn_fallback`, `digest_name_collision`, `digest_interrupted_fallback`, средний `digest_chars`.
- Уплотнение: снято правилом 1, правилом 2, правилом 3 (`suppressed_by_rule_1/2/3`).
- Задержки хуков: p50/p95/max `duration_ms` по каждому хуку, доля таймаутов, доля ходов с `deadline_remaining_ms < return_min_budget_ms`.
- Сжатие: число обнаружений, сработавший порог (`msgs`/`chars`), срабатывания cooldown, `return_injection_limit`.
- Конфигурация: `config_hash`, `minimem_version`, `config_changed`, `config_invalid`.
- Состояние: доля прерванных сессий (`completed_state`), доля записей `withheld`, доля записей с `turn_source: derived`.
