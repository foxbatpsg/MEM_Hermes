# MiniMem-1 — Решения по вопросам и план внесения правок (на основе «План правок ТЗ v1.6»)

Целевой документ для всех пунктов, если не указано иное: `MiniMem-1 - Техническое задание v1.6.md`.
Правки вносятся как редакция v1.7. Пункты пронумерованы как в плане правок (П-NN).

## 0. Решения по открытым развилкам плана

0.1. П-02 (конфликт event_id). Решение: принимается только вариант «ревизии записи» (revision/supersedes). Альтернативный вариант с `event_id = hash(..., ordinal)` и полем `conflict_of` из плана правок исключить, в ТЗ не вносить.

0.2. П-09 (отсутствие session_id). Решение: ход всегда сохраняется, потеря запрещена. При отсутствии session_id — сессия `unknown-<дата>`, проект `common`, `session_source = derived`, событие в лог обязательно.

0.3. Дефект нумерации в плане правок: тесты MM-155/MM-156/MM-157 определены дважды — для П-02 и для П-16 — с разным содержанием. Решение: тесты П-02 переносятся на номера MM-162, MM-163, MM-164. За П-16 остаются MM-155, MM-156, MM-157 без изменений.

0.4. Итоговый диапазон новых тестов после исправления нумерации: MM-116…MM-164 (вместо разночтений «…MM-154» и «…MM-157» в разных разделах плана правок). Везде далее использовать этот диапазон.

0.5. Ссылка «раздел 5» в блоке «Обозначения» плана правок битая (раздела 5 в этом документе нет). Решение: пункты Р-NN «развитие на будущее» ведутся только в файле `MiniMem-1 - Реестр доработок после эксплуатации.md`, разделе «Развитие на будущее от DS». В плане правок и в ТЗ ссылку на «раздел 5» не использовать.

0.6. Численные параметры детекции сжатия контекста (П-04), не заданные числом в плане правок, зафиксировать так:
- `compaction_shrink_ratio = 0.6`
- `compaction_min_drop = 6` (сообщений)
- `compaction_min_chars_drop = 3000` (символов)
- `compaction_cooldown_turns = 2`
- `max_return_injections_per_session = 3`

### П-04. Детекция сжатия контекста

### П-06. Разложение бюджетов времени хуков
- Где: §19.1, §18.1, §11, §20, §21.

## 3. Эксплуатационные правки (P2)

### П-13. Блокировка журнала, контроль append, повторы лога о повреждении
- Где: §4.5.1, §4.5.2, §4.5.3, §19.3, §22, §21.
- Изменить на:
  1. Единый интерфейс блокировки: Windows — `msvcrt.locking` по байтовому диапазону либо lockfile; POSIX — `fcntl.flock(LOCK_EX)`. Порядок: lock → seek в конец → write одной записью → flush → fsync → unlock.
  2. После записи сверять размер файла и наличие завершающего маркера; при несовпадении — `journal_append_unverified`, курсор за эту запись не продвигается.
  3. На POSIX при создании нового дневного файла дополнительно `fsync` каталога.
  4. О повреждённой записи писать одну строку лога на связку (файл, смещение, mtime); повторные обнаружения — счётчиком в `stats`, не новой строкой лога.
  5. §21: `verify` — проверка непрерывности файла (size/mtime относительно курсора) и событие `journal_externally_modified`.
- Проверить: MM-148, MM-149, MM-150.
