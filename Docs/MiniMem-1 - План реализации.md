# MiniMem-1 — План реализации

Основание: «MiniMem-1 - Техническое задание v1.5» (далее — ТЗ) и «MiniMem-1 - Установка,
бэкап и восстановление». План задаёт порядок работ, состав файлов и то, что проверяется
на каждом этапе. Нумерация тестов — по разделу 23 ТЗ.

---

## 1. Решения, принятые в плане

Все решения окончательные, открытых вопросов не остаётся.

- **Интерпретатор:** Python 3.11 из окружения Hermes
  (`hermes-agent\venv\Scripts\python.exe`). Проверено на этой машине: Python 3.11.16,
  SQLite 3.53.1, FTS5 доступен.
- **Зависимости:** только стандартная библиотека. Ни одного пакета в окружение Hermes
  не устанавливается.
- **Код:** `C:\Projects\MEM_Hermes\minimem\`. Конфигурация — `config.json` рядом с кодом
  (JSON: разбор средствами стандартной библиотеки, без зависимостей).
- **Данные:** `<memory_root>` — внутри хранилища, предлагаемый путь
  `C:\Projects_loc\LLM_Wiki\memory`. Путь задаётся в `config.json`; требование ТЗ —
  внутри хранилища, чтобы журнал был виден человеку и Obsidian.
- **Хуки:** три тонких скрипта. Каждый читает stdin, вызывает модуль, пишет stdout,
  всегда завершается кодом 0. Вся логика — в модулях, не в скриптах хуков.
- **Тесты:** `unittest`, каталог `tests/`, запуск
  `python -m unittest discover -s tests`. Номер теста по ТЗ пишется в docstring строкой
  `MM-NN`. Список обязательных номеров — `tests/required_tests.txt`; тест
  `tests/test_required_numbers.py` сверяет, что каждый обязательный номер присутствует
  в прогоне (реализует раздел «Обязательные номера» ТЗ).
- **Кодировка и переводы строк:** UTF-8 указывается явно при каждом открытии файла;
  в журнале — LF; запись — append под блокировкой.
- **Порядок изменения документации:** сначала правка в ТЗ, затем код. Документ не должен
  отстать от кода.

## 3. Этапы

### Этап 0. Каркас

**Цель:** пути, конфигурация, лог, CLI.

**Что делаем:** `config.json` со значениями раздела 20; `paths.py`; `log.py`; `project.py`(определение проекта по `cwd`, неизвестный проект — `common`); каркас `minimem.py`
с командами `status` и `verify` (пока без проверок).

**Критерий готовности:** `minimem status` печатает путь журнала, число файлов, состояние SQLite; `minimem verify` выполняется без ошибок; лог пишется; проект из тестового `cwd` определяется правильно.  
После успешного завершения Этапа 1 формат Journal считается стабилизированным. Изменение формата после этой точки допускается только через изменение ТЗ и процедуру миграции/совместимости.

**Тесты ТЗ:** нет (инфраструктура для всех последующих).

---

### Этап 1. Захват и журнал (модуль 1)

**Цель:** одна запись на завершённый ход, журнал как источник истины.

**Что делаем:** `redaction.py` (удаление секретов до записи), обрезка по лимитам,`canonical.py` (канонизация и оба хэша), `journal.py` (запись по разделу 4.4 с маркерами, экранированием и блокировкой; разбор обратно), idempotency по `event_id`, признак обрезки `truncated`, хук `post_llm.py`.

**Файлы:** `mm/redaction.py`, `mm/canonical.py`, `mm/journal.py`, `hooks/post_llm.py`.

**Критерий готовности:** реплика и ответ попадают в дневной файл журнала; файл читается как обычный Markdown; повторная доставка того же события не создаёт второй записи; секреты в журнале отсутствуют.

**Тесты ТЗ:** 1–8, 13, 14.

> С этого этапа журнал начинает накапливать реальные записи — с него же запускается ежедневное резервное копирование по документу «Установка, бэкап и восстановление».

---

### Этап 2. Индексатор и служебный слой (модуль 6)

**Цель:** SQLite/FTS5 как производный слой с самовосстановлением.

**Что делаем:** схема `store.py` (FTS5-поля и служебные колонки, `schema_version`,
`rebuilt_at`, счётчики, список снятых, состояние сессий, WAL и `busy_timeout`);
`indexer.py` — добавление записей, которых нет в индексе, по `event_id`; команды
`rebuild-index`, `show`, `verify`; фильтр по проекту.

**Файлы:** `mm/store.py`, `mm/indexer.py`, расширение `minimem.py`.

**Критерий готовности:** новая запись появляется в FTS5; удаление `minimem.db` и `rebuild-index` полностью восстанавливает индекс; `verify` находит запись журнала, отсутствующую в индексе; индексатор не удаляет запись журнала при своей ошибке.

**Тесты ТЗ:** 9, 10, 11, 15, 16, 42.

---

### Этап 3. Дайджест (модуль 4)

**Цель:** детерминированная выжимка последних ходов сессии.

**Что делаем:** `digest.py` — последние `digest_turns` ходов, исключение снятых записей, ограничение `max_digest_chars`, заголовок с пометкой «выжимка, а не пересказ», запись в `memory_root/<project>/memory/digest/<session_id>.md`; команда `rebuild-digest`
с параметрами `--session` и `--all`.

**Файлы:** `mm/digest.py`, расширение `minimem.py`.

**Критерий готовности:** файл дайджеста создаётся на `on_session_end` и пересоздаётся из журнала по команде; снятые записи в него не попадают; размер в пределах лимита.

**Тесты ТЗ:** 31, 32, 33.

---

### Этап 4. Возврат (модуль 2) и хук `pre_llm_call`

**Цель:** выжимка на первом ходе новой сессии и после сжатия контекста.

**Что делаем:** `ret.py` — выбор файла дайджеста по правилам раздела 11; `session.py` — разбор события хода, `is_first_turn`, вычисление сжатия контекста по `max_history_len` с порогами `compaction_shrink_ratio` и `compaction_min_drop`; `insert.py` — формат вставки по разделу 13; хук `pre_llm.py`, который на первом ходе выполняет catch-up, затем Возврат.
При сжатии контекста дайджест текущей сессии создаётся модулем Дайджест до чтения.

**Файлы:** `mm/ret.py`, `mm/session.py`, `mm/insert.py`, `hooks/pre_llm.py`.

**Критерий готовности:** на первом ходе новой сессии вставляется выжимка предыдущей сессии; на ходе с резко сократившейся историей — выжимка текущей сессии; пустой вывод хука не меняет сообщение пользователя; объём вставки в пределах `max_return_chars`.

**Тесты ТЗ:** 17–21, 30, 45, 46.

---

### Этап 5. Поиск по реплике (модуль 3)

**Цель:** релевантные записи на содержательных ходах.

**Что делаем:** `query.py` — разбиение реплики на слова, отсев коротких, детерминированное усечение до основы по фиксированному списку окончаний, сборка запроса из основ с префиксом через `OR` (раздел 12 ТЗ); `search.py` — фильтр по проекту, исключение снятых и уже возвращённых, порог `search_score_threshold` в шкале `score = -bm25(...)` (больше — лучше), лимиты, увеличение `usage_count`, отметка в состоянии сессии;
вставка результата через `insert.py`.

**Файлы:** `mm/query.py`, `mm/search.py`, расширение `hooks/pre_llm.py`.

**Критерий готовности:** содержательная реплика находит релевантные записи, в том числе при другом окончании слова; короткая служебная — не ищет; одна запись не возвращается дважды; текст пользователя не меняет структуру FTS5-запроса.
Калибровка search_score_threshold на реальном журнале является обязательной частью приёмки этапа. После фиксации значения выполняется повторный прогон тестов.

**Тесты ТЗ:** 12, 22–29, 48, 49, 50.

**Отдельная задача этапа — калибровка `search_score_threshold`.** Набрать 20 реальных реплик из накопленного журнала, прогнать поиск, подобрать порог так, чтобы содержательные реплики находили нужное, а служебные — нет. Значение зафиксировать в `config.json` и обновить
раздел 20 ТЗ. При калибровке проверить направление сравнения: запись проходит при `score >= search_score_threshold`, где `score = -bm25(...)`; в шкале bm25 «меньше — лучше», поэтому знак имеет значение.

---

### Этап 6. Уплотнение (модуль 5)

**Цель:** механическое снятие записей с поиска без удаления истории.

**Что делаем:** `compaction.py` — три правила раздела 15, включая ограничение
`timestamp > rebuilt_at` и «первая запись остаётся»; точный дубль — только внутри одного проекта; сохранение снятых в служебном слое со ссылкой на `event_id`; пересчёт снятых при `rebuild-index` только по правилам 1 и 3; команда `compact`.

**Файлы:** `mm/compaction.py`, расширение `minimem.py`.

**Критерий готовности:** записи журнала не удаляются; снятые не возвращаются поиском и не попадают в дайджест; после `rebuild-index` снятые по правилам 1 и 3 остаются снятыми, а снятые только по правилу 2 возвращаются в поиск; одинаковое содержимое в разных проектах дублем не считается.

**Тесты ТЗ:** 34–39, 43, 44.

---

### Этап 7. Жизненный цикл, сессии, надёжность

**Цель:** связать модули в работу по разделам 17–19.

**Что делаем:** состояние сессии целиком (`returned_event_ids`, `last_known_turn`,
`max_history_len`, `digest_status`, `pending_catch_up`); catch-up на первом ходе
(Уплотнение, затем Дайджест предыдущей сессии) с повтором при `pending_catch_up`;
`on_session_end` (Уплотнение, затем Дайджест); таймауты 15 и 30 с с прерыванием по времени;
изоляция ошибок — любой отказ логируется и не останавливает Hermes.

**Файлы:** `mm/session.py` (дополнение), `hooks/session_end.py`, правки всех хуков.

**Критерий готовности:** отказ любого модуля не ломает ход Hermes; `pre_llm_call`
укладывается в 15 с; прерванный catch-up повторяется на следующем ходу.

**Тесты ТЗ:** 40, 41.

---

### Этап 8. Установка и приёмка

**Цель:** подключить MiniMem к Hermes и принять работу.

**Что делаем:** записать три хука в `%LOCALAPPDATA%\hermes\config.yaml` по разделу 26 ТЗ;
подтвердить команды; проверить `hermes hooks list` и `hermes hooks doctor`; прогнать
все 50 тестов; выполнить критерии раздела 25; сделать первый живой прогон на реальном
проекте и проверить журнал, индекс, дайджест и возврат на следующей сессии; убедиться,
что резервное копирование журнала работает.

**Критерий готовности:** все приёмочные тесты проходят; отчёт о прогоне содержит все
обязательные номера; новая сессия получает выжимку прошлой; содержимое журнала
соответствует разделу 4.4.

**Тесты ТЗ:** 47 и полный прогон 1–50.

## 4. Правила работы по плану

1. Один этап — одна законченная функциональная подсистема / зона ответственности. Следующий этап не начинается, пока не пройдены тесты предыдущего.
2. Тесты пишутся в том же этапе, что и код, и несут номер из раздела 23 ТЗ.
3. Тест нельзя удалить: только перевести в статус «снят» с указанием причины (раздел 23).
4. Заглушек «потом доделаю» не бывает. Если функциональность не входит в MiniMem-1, она не пишется вовсе.
5. Любая ошибка перехватывается на границе хука: запись в лог, пустой вывод, Hermes продолжает работу (раздел 19.2).
6. Изменение поведения сначала вносится в ТЗ, затем в код.
7. Журнал копируется в бэкап ежедневно, начиная с этапа 1.

## 6. Риски

| Риск | Где проявляется | Что делаем |
|---|---|---|
| Таймаут 15 с на `pre_llm_call` | этапы 4, 5, 7 | тяжёлое выносится в catch-up; измеряется `duration_ms`; при нехватке времени работа прерывается и логируется (раздел 19.1) |
| Одновременная запись в журнал из двух сессий | этап 1 | append под блокировкой; при неудаче — повтор и запись в лог |
| Кодировка и CRLF на Windows | этап 1 | UTF-8 явно, LF явно, `newline=''` при записи |
| Русская морфология в поиске | этап 5 | решено в ТЗ v1.5 (раздел 12): детерминированное усечение основы + prefix-поиск; качество проверяется тестами 48–50 и калибровкой порога |
| Слишком широкое prefix-сопоставление | этап 5 | лимиты `max_return_records` и `max_return_chars`, порог `search_score_threshold`, тест 50 |
| Обновление Hermes переписывает `config.yaml` | этап 8 и далее | после каждого обновления — `hermes hooks doctor` (документ по установке) |
| Рост журнала | эксплуатация | уплотнение не удаляет записи; размер контролируется, вынос старых файлов — за пределами MiniMem-1 |
| Потеря журнала при сбое Windows | всегда | ежедневный бэкап с этапа 1; восстановление по документу «Установка, бэкап и восстановление» |
