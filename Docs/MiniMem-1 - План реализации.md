# MiniMem-1 — План реализации v1.6

Основание: «MiniMem-1 - Техническое задание v1.6» и «MiniMem-1 - Реестр доработок после эксплуатации».
План задаёт порядок работ, состав файлов и то, что проверяется на каждом этапе.
Нумерация тестов — по разделу 23 ТЗ v1.6.

## 1. Решения, принятые в плане

Все решения, принятые в плане v1.5, остаются действительными, если не изменены планом правок v1.6.

Открытые эксплуатационные решения фиксируются в файле:

MiniMem-1 - Реестр доработок после эксплуатации.md

Интерпретатор: Python 3.11 из окружения Hermes
(`hermes-agent\venv\Scripts\python.exe`). Проверено на этой машине: Python 3.11.16,
SQLite 3.53.1, FTS5 доступен.

Зависимости: только стандартная библиотека. Ни одного пакета в окружение Hermes
не устанавливается.

Код: `C:\Projects\MEM_Hermes\minimem\`. Конфигурация — `config.json` рядом с кодом
(JSON: разбор средствами стандартной библиотеки, без зависимостей).

Данные: `<memory_root>` — внутри хранилища, предлагаемый путь
`C:\Projects_loc\LLM_Wiki\memory`. Путь задаётся в `config.json`; требование ТЗ —
внутри хранилища, чтобы журнал был виден человеку и Obsidian.

Хуки: три тонких скрипта. Каждый читает stdin, вызывает модуль, пишет stdout,
всегда завершается кодом 0. Вся логика — в модулях, не в скриптах хуков.

Тесты: `unittest`, каталог `tests/`, запуск
`python -m unittest discover -s tests`. Номер теста по ТЗ пишется в docstring строкой
`MM-NN`. Список обязательных номеров — `tests/required_tests.txt`; тест
`tests/test_required_numbers.py` сверяет, что каждый обязательный номер присутствует
в прогоне.

Кодировка и переводы строк: UTF-8 указывается явно при каждом открытии файла;
в журнале — LF; запись — атомарный append под блокировкой.

Порядок изменения документации: сначала правка в ТЗ, затем план, затем
`tests/required_tests.txt`, затем код. Документ не должен отстать от кода.

## 3. Этапы

### Этап 0. Каркас

Цель: пути, конфигурация, режимы, лог, CLI, проект, timezone.

Что делаем:
- `config.json` со значениями раздела 20 ТЗ v1.6;
- загрузка `mode_capture`, `mode_return`, `mode_search`, `mode_compaction`;
- `compaction_rule2_enabled`;
- `journal_fsync`, `journal_timezone`;
- `catch_up_retry_max_turns`, `catch_up_budget_seconds`;
- `paths.py`;
- `log.py` с расширенными полями;
- `project.py` с Windows-нормализацией;
- каркас `minimem.py` с командами `status` и `verify`;
- `status` показывает режимы и ключевые флаги.

Критерий готовности:
- `minimem status` печатает путь журнала, число файлов, состояние SQLite, активные режимы;
- `minimem verify` выполняется без ошибок;
- лог пишется;
- проект из тестового `cwd` определяется правильно с учётом регистра и вложенности;
- конфигурация читается и значения по умолчанию корректны.

Тесты ТЗ: инфраструктурные, обязательных приёмочных тестов нет.

### Этап 1. Захват и журнал

Цель: одна каноническая запись на завершённый ход, журнал как надёжный источник истины.

Что делаем:
- `redaction.py` с placeholder'ами;
- `canonical.py`: `content_hash` до обрезки, `event_id` по `project+session_id+task_id+turn`;
- `journal.py`: атомарная запись, `msvcrt.locking`, `fsync` flag, разбор с nested `mm:begin`;
- контроль `max_memory_record`;
- idempotency/conflict policy;
- поведение при недоступном SQLite;
- минимальная SQLite-таблица `capture_guard` как best-effort идемпотентный гард;
- хук `post_llm.py` с `mode_capture` gate.

Файлы:
- `mm/redaction.py`
- `mm/canonical.py`
- `mm/journal.py`
- `mm/store.py` — минимальная часть: `meta`, `capture_guard`
- `hooks/post_llm.py`

Критерий готовности:
- реплика и ответ попадают в дневной файл журнала;
- файл читается как обычный Markdown;
- повторная доставка того же логического хода не создаёт вторую каноническую запись;
- конфликт `content_hash` логируется;
- секреты заменяются placeholder'ами и не попадают в журнал;
- фрагменты секретов не попадают в лог;
- частичная запись не повреждает следующую запись;
- вложенный `mm:begin` корректно обрабатывается;
- запись не превышает `max_memory_record`;
- при недоступном SQLite запись всё равно сохраняется и логируется guard unavailable.

Тесты ТЗ:
- 1–8, 13, 14;
- MM-51, MM-61–MM-67, MM-69, MM-85, MM-89, MM-102, MM-106, MM-114.

С этого этапа журнал начинает накапливать реальные записи — с него же запускается ежедневное резервное копирование.

Формат журнала считается стабилизированным только после успешного завершения этого этапа.

### Этап 2. Индексатор и служебный слой

Цель: SQLite/FTS5 как производный слой с инкрементальной индексацией и самовосстановлением.

Что делаем:
- `store.py`: `memory_fts`, `memory_meta`, `capture_guard`, `usage_counters`, `suppressed_records`, `sessions`, `session_returns`, `journal_cursors`, `meta`;
- индексы по `project/session/turn`, `project/timestamp_utc`, `content_hash/project`;
- `indexer.py`: курсоры, batch limit, duplicate `event_id`, damaged records;
- команды `rebuild-index`, `show`, `verify`;
- фильтр по проекту;
- `verify` проверяет duplicate, missing metadata, cursor validity.

Файлы:
- `mm/store.py`
- `mm/indexer.py`
- расширение `minimem.py`

Критерий готовности:
- новая запись появляется в FTS5 и `memory_meta`;
- удаление `minimem.db` и `rebuild-index` полностью восстанавливает индекс;
- `verify` находит запись журнала, отсутствующую в индексе;
- индексатор не удаляет запись журнала при своей ошибке;
- индексатор штатно не читает весь дневной файл;
- после сбоя индексатора пропущенная запись догоняется;
- duplicate `event_id` обрабатывается детерминированно;
- `content_hash` не пересчитывается из обрезанного текста.

Тесты ТЗ:
- 9, 10, 11, 15, 16, 42;
- MM-53, MM-57, MM-59, MM-60, MM-64, MM-65, MM-70, MM-71, MM-73, MM-103.

### Этап 3. Дайджест

Цель: детерминированная выжимка последних ходов сессии.

Что делаем:
- `digest.py`;
- последние `digest_turns` ходов;
- исключение снятых записей;
- `max_digest_chars`;
- filesystem-safe имя файла;
- заголовок с нормативным полем `Создан`;
- обработка повреждённого дайджеста;
- команда `rebuild-digest` с `--session` и `--all`.

Файлы:
- `mm/digest.py`
- расширение `minimem.py`

Критерий готовности:
- файл дайджеста создаётся на `on_session_end` и пересоздаётся из журнала по команде;
- снятые записи в него не попадают;
- размер в пределах лимита;
- имя файла безопасно для Windows;
- поле `Создан` записывается в ISO-8601 с offset.

Тесты ТЗ:
- 31, 32, 33.

### Этап 4. Возврат и хук pre_llm_call

Цель: выжимка при наличии дайджеста и после сжатия контекста Hermes.

Важно: полноценный automatic catch-up с уплотнением предыдущей сессии переносится в Этап 7.
На этом этапе Return работает с уже существующими дайджестами.

Что делаем:
- `ret.py`: выбор дайджеста по разделу 11.1;
- `session.py`: разбор события хода, `is_first_turn`, детекция сжатия контекста с удалением блоков MiniMem;
- `insert.py`: формат вставки и санитизация делимитеров;
- `hooks/pre_llm.py` с `mode_return` и `mode_search` gates;
- при сжатии контекста и `mode_return=true` дайджест текущей сессии создаётся при необходимости.

Файлы:
- `mm/ret.py`
- `mm/session.py`
- `mm/insert.py`
- `hooks/pre_llm.py`

Критерий готовности:
- при наличии дайджеста предыдущей сессии на первом ходе вставляется выжимка;
- на ходе с резко сократившейся историей вставляется выжимка текущей сессии;
- пустой вывод хука не меняет сообщение пользователя;
- объём вставки в пределах `max_return_chars`;
- при `mode_return=false` ничего не вставляется;
- блоки памяти MiniMem не ломают границу вставки;
- измерение history length не искажается блоками MiniMem.

Тесты ТЗ:
- 17–21, 30, 45, 46;
- MM-109.

### Этап 5. Поиск по реплике

Цель: релевантные записи на содержательных ходах.

Что делаем:
- `query.py`: слова, отсев коротких, усечение основ, уникальность, `max_search_terms`, zero-term skip;
- `search.py`: фильтр по проекту, исключение снятых и возвращённых, порог, лимиты, `usage_count`;
- вставка результата через `insert.py`;
- калибровка `search_score_threshold`.

Файлы:
- `mm/query.py`
- `mm/search.py`
- расширение `hooks/pre_llm.py`

Критерий готовности:
- содержательная реплика находит релевантные записи;
- короткая служебная не ищет;
- одна запись не возвращается дважды;
- текст пользователя не меняет структуру FTS5-запроса;
- количество терминов не превышает `max_search_terms`;
- при нулевых терминах поиск не запускается.

Тесты ТЗ:
- 12, 22–29, 48, 49, 50.

Отдельная задача этапа — калибровка `search_score_threshold`. Набрать 20 реальных реплик из накопленного журнала, прогнать поиск, подобрать порог так, чтобы содержательные реплики находили нужное, а служебные — нет. Значение зафиксировать в `config.json` и обновить
раздел 20 ТЗ. При калибровке проверить направление сравнения: запись проходит при `score >= search_score_threshold`, где `score = -bm25(...)`; в шкале bm25 «меньше — лучше», поэтому знак имеет значение.

### Этап 6. Уплотнение

Цель: механическое снятие записей с поиска без удаления истории.

Что делаем:
- `compaction.py`;
- правила 1 и 3 всегда;
- правило 2 только при `compaction_rule2_enabled=true`;
- tie-breaker по `timestamp_utc`, `turn_numeric`, `turn`, `event_id`;
- сохранение снятых в `suppressed_records`;
- `rebuild-index` restoration по правилам 1 и 3;
- команда `compact`;
- `mode_compaction` gate для автоматического уплотнения.

Файлы:
- `mm/compaction.py`
- расширение `minimem.py`

Критерий готовности:
- записи журнала не удаляются;
- снятые не возвращаются поиском и не попадают в дайджест;
- после `rebuild-index` снятые по правилам 1 и 3 остаются снятыми;
- снятые только по правилу 2 возвращаются в поиск;
- одинаковое содержимое в разных проектах дублем не считается;
- при `compaction_rule2_enabled=false` правило 2 не работает.

Тесты ТЗ:
- 34–39, 43, 44;
- MM-54, MM-79.

### Этап 7. Жизненный цикл, сессии, catch-up, надёжность

Что делаем:

- `on_session_end`: уплотнение, затем дайджест;
- таймауты 15 и 30 с;
- изоляция ошибок;
- повтор catch-up с лимитом attempts;

Файлы:
- `mm/session.py` (дополнение)
- `hooks/session_end.py`
- правки всех хуков

Критерий готовности:
- отказ любого модуля не ломает ход Hermes;
- `pre_llm_call` укладывается в 15 с;
- прерванный catch-up повторяется ограниченно и не дублирует операции;
- при `mode_compaction=false` автоматическое уплотнение не выполняется;
- при `mode_return=false` дайджест на `on_session_end` всё равно создаётся;
- переключение режимов не требует `rebuild-index`.

Тесты ТЗ:

## 4. Правила работы по плану

Один этап — одна законченная функциональная подсистема / зона ответственности.
Следующий этап не начинается, пока не пройдены тесты предыдущего.
Тесты пишутся в том же этапе, что и код, и несут номер из раздела 23 ТЗ.
Тест нельзя удалить: только перевести в статус «снят» с указанием причины.
Заглушек «потом доделаю» не бывает. Если функциональность не входит в MiniMem-1, она не пишется вовсе.
Любая ошибка перехватывается на границе хука: запись в лог, пустой вывод, Hermes продолжает работу.
Изменение поведения сначала вносится в ТЗ, затем в код.
Журнал копируется в бэкап ежедневно, начиная с этапа 1.
Отложенные эксплуатационные решения фиксируются в реестре доработок.

## 5. Что не входит в реализацию

Без изменений от v1.5, плюс:
- автоматическое включение правила 2 уплотнения без RB-01;
- агрессивный catch-up варианта B без RB-02;
- фоновый maintenance индексатора.

## 6. Риски

| Риск | Где проявляется | Что делаем |
|---|---|---|
| Частичная запись журнала | этап 1 | атомарная запись, блокировка, nested mm:begin |
| Duplicate event_id | этапы 1, 2 | first-write-wins, capture_guard, indexer dedup, verify |
| Недоступный SQLite при Capture | этап 1 | пишем журнал, логируем guard unavailable |
| Деградация индексатора | этап 2 | journal_cursors, batch limit |
| Таймаут catch-up | этапы 4, 7 | бюджет 8 с, retry max 2, pending state |
| Ложные дубликаты из-за обрезки | этапы 1, 6 | content_hash до обрезки |
| Преждевременное уплотнение | этап 6 | rule2 disabled by default |
| Delimiter injection | этапы 4, 5 | санитизация вставки |
| Слабый русский поиск | этап 5 | max_search_terms, калибровка, RB-05 |
| Обновление Hermes переписывает config.yaml | этап 8 и далее | после каждого обновления — hermes hooks doctor |
| Рост журнала | эксплуатация | уплотнение не удаляет записи; размер контролируется, вынос старых файлов — за пределами MiniMem-1 |
| Потеря журнала при сбое Windows | всегда | ежедневный бэкап с этапа 1; восстановление по документу «Установка, бэкап и восстановление» |
